A GitLab feature designed to let users create work items through email can be abused as an account-level code delivery mechanism, potentially allowing attackers to push commits to protected branches and execute CI/CD pipelines when a private incoming-email address is exposed. Security researcher Joe Leon of Aikido Security found that GitLab’s “Email work item to this project” option generates an address containing a long-lived incoming email token. Although GitLab presents the address as a project-specific method for creating issues, the embedded credential can apply across every project the affected user can access. GitLab Email Feature Lets Attackers Push Code The address follows a format similar to incoming+project-id-glimt- -issue@incoming.gitlab.com . The glimt- value acts as an authentication token that does not expire by default. Aikido’s research found that the same token appears in email addresses generated for multiple projects, including private repositories , making it an account-scoped credential rather than a project-scoped one. An attacker who obtains a victim’s incoming-email address can reportedly change the address suffix from -issue to -merge-request and submit a Git patch as an attachment. By specifying a source branch in the email subject, the attacker can cause GitLab to apply the patch to an existing branch or create a new branch under the victim’s identity.
