Your Zimbra server is under threat. Recently our PT ESC IR team encountered a new ransomware group attack on Zimbra mail servers using vulnerability CVE-2026-73570 and the TargetZimbra encryptor. According to open sources, similar attacks have been massively recorded on Zimbra servers since mid-August.

*Disclaimer: if you are using an outdated version of Zimbra software and have not detected the indicators of compromise of the specific TargetZimbra ransomware campaign on your mail server, this does not mean your server is guaranteed not compromised. CVE-2026-73570 can be used by other attackers, for example, to install miners, as well as APT groups targeting compromise of the entire organization's infrastructure.*

CVE-2026-73570 allows an attacker to inject and execute malicious commands on the Zimbra mail server with zimbra user privileges without prior authentication due to insufficient input sanitization in the SNMP component.

For successful exploitation, the mail server must have Zimbra Collaboration Suite version below 10.1.20 installed, along with the zimbra-snmp package and SNMP notifications enabled. The vulnerability is exploited by sending a specially crafted SMTP request through ports 25, 465, or 587.

**Attack scenario:**

1. By exploiting CVE-2026-73570, attackers create a file `/opt/zimbra/jetty_base/webapps/zimbra/public/version.txt` (or `versions.txt`) on the mail server containing information about the Zimbra software version used on the server. The created file serves as an indicator of successful vulnerability exploitation for the attacker.

2. At the next stage, attackers upload JSP shells to the mail server directory `/opt/zimbra/jetty_base/webapps/zimbra/public/`. Additionally, the hacking tool Gsocket was recorded being injected onto the server.

3. Next, attackers upload the TargetZimbra encryptor written in Go language. After launch, the malicious module encrypts files using the ChaCha20 algorithm in the /opt/zimbra/ directory and its subdirectories.

4. After file encryption, the encryptor changes their extension to `.elock` and creates files `!README_RECOVER.txt` in encrypted directories containing contact information and ransom payment details. Upon completion, the TargetZimbra malicious module deletes itself from the system.

**How to check your Zimbra mail server for signs of compromise:**

1. In the main system log of the mail service `/var/log/maillog`, records containing the substring `changed from stopped to`, preceded by a shell command or other suspicious payload, are indicators of CVE-2026-73570 exploitation.

Search command: `grep "changed from stopped to" /var/log/maillog`

2. Presence of non-standard JSP files not related to Zimbra software that were created or modified in recent months in the directory `/opt/zimbra/jetty_base/webapps/zimbra/` and all its subdirectories. Characteristic features of malicious JSP files include obfuscated code, encoded strings, and atypical handling of GET and POST requests.

Search commands:
`find /opt/zimbra/jetty_base/webapps/zimbra/ -type f -iname '*.jsp' -newermt '2026-07-01'` (search by file modification date)
`find /opt/zimbra/jetty_base/webapps/zimbra/ -type f -iname '*.jsp' -newerBt '2026-07-01'` (search by file creation date)

Note: not all Linux file systems store file creation date. Also check the server with antivirus tools.

3. In the web server access log (e.g., for Nginx web server standard location `/var/log/nginx/access.log`), records of access to non-standard JSP files (with response code 200) located in `/opt/zimbra/jetty_base/webapps/zimbra/` and all its subdirectories (including the commonly used directory `/opt/zimbra/jetty_base/webapps/zimbra/public/`) may indicate the presence of web shells on the mail server.

**Recommendations:**

1. Update Zimbra software on your mail server to the latest version. Ideally, also reinstall the server OS with migration of all mail data.

2. If immediate software update is not possible, a temporary solution may be disabling SNMP notifications and removing the `zimbra-snmp` package.

3. Additionally, check the mail server with antivirus tools and manually inspect non-standard JSP files created in recent months in Zimbra service directories.

**Indicators of Compromise:**

File indicators:
- `/opt/zimbra/jetty_base/webapps/zimbra/public/version.txt` or `versions.txt` - file containing Zimbra software version
- `/opt/zimbra/jetty_base/webapps/zimbra/public/[Filename].jsp` - web shell
- `/opt/zimbra/log/defunct` - Gsocket
- `elockc[a-z]` (e.g., `elockcl`) - encryptor
- `runloop.sh` - script created by encryptor
- `!README_RECOVER.txt` - attacker's note
- `*.elock` - files with `.elock` extension
