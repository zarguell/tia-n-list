Where Kubernetes audit logs live depends on who runs your control plane. On a self-managed cluster, they’re a JSON-lines file on the control plane node, at whatever path –audit-log-path points to. On EKS, they go to CloudWatch Logs, on AKS to a Log Analytics workspace or storage account, and on GKE to Cloud Audit Logs. One thing holds everywhere: audit logging has to be switched on. On self-managed clusters and EKS it’s off until someone enables it. The audit log records every request to the Kubernetes API: who ran kubectl exec into which pod, who read which secret, who bound themselves to cluster-admin. Prime Core has 93 detection rules for Kubernetes audit data, mapped to 220 MITRE ATT&CK techniques. Among them: exec into running containers (T1609), deploying rogue containers (T1610) and reading credentials through the container API (T1552.007).
