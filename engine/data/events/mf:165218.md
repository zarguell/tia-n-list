An attacker with Global Administrator or Authentication Policy Administrator privileges can register a rogue External Authentication Method (EAM) in Entra . Entra then treats the attacker-controlled service as an MFA provider for users assigned to it. The provider needs an application registration, a service principal and a publicly reachable HTTPS address. The user first enters their password on Microsoft’s real sign-in page. When MFA starts, Entra redirects the browser to the rogue provider. Instead of asking for a second factor, that provider displays a convincing copy of Microsoft’s password page. If the user enters the password again, the attacker-controlled server records it in plaintext. The provider then sends Entra a signed token claiming that the authentication check passed. Entra validates the token and completes the sign-in. In Varonis’s test tenant, users reached their applications without errors, while the researchers’ server received their passwords, timestamps and source IP addresses. The discovery document tells Entra where the provider lives (Source: varonis) Varonis built its proof of concept with a small OpenID Connect server. Its discovery document told Entra where to find the provider, while its public key let Entra verify returned tokens. The attack works because a valid token does not prove that the provider showed the user a genuine MFA challenge . The researchers’ server claimed a hardware-key check had succeeded after collecting a password instead.
