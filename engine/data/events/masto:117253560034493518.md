[Translation] The Lifecycle of an API Token: From Issuance to Revocation. API tokens are often treated as minor implementation details. A user logs in, the server creates a token, the browser stores it and includes it in every protected request. On the surface the process looks simple.

The security consequences are anything but simple. A token can be correctly signed and still stolen. It can use strong cryptography and still remain active long after an attacker gains access. A signature protects a token from modification, not from theft.

For browser applications, token security depends not just on the JWT algorithm chosen. It depends on how the token is issued, where it is stored, how it is transmitted and refreshed, how quickly it can be revoked, and whether suspicious activity can be detected before serious consequences follow.

The article walks through the full lifecycle across six stages: token issuance (choosing the right OAuth flow, short-lived access tokens, protecting authorization endpoints), client-side storage (avoiding localStorage for sensitive tokens, HttpOnly cookies, the Backend-for-Frontend pattern), transmission and usage (bearer tokens vs cookies, never putting tokens in URLs, log hygiene, replay attacks), refresh token rotation (atomic rotation, detecting token reuse, preventing concurrent refresh requests), expiration and revocation (token blocklists, session records, token family tracking), and monitoring and detection (suspicious refresh patterns, honeytokens, token size limits).
