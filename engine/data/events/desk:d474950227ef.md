Mehmet Ince's writeup describes a type-confusion primitive in PostgreSQL composite types triggered by preparing a query, altering a field's type, and executing it, which crashes the backend as a lowest-privileged login role and can be developed into code execution. The post explains that prepared values are not rewritten when a field type changes, so bytea output functions interpret stale bytes as an expanded-object header and pointer. The researcher notes the expanded-object pointer mechanism was introduced on May 14, 2015 and that reproducible proofs of concept were privately shared with managed PostgreSQL providers' security teams around mid-August 2026. The issue is fixed by the PostgreSQL security release published November 12, 2026.
