Product: WPIDE – File Manager & Code Editor for WordPress Affected: 3.6.0 – 3.6.4 (bypass verified against 3.6.0–3.6.2) Fixed: 3.6.5 (3.6.4 + 3.6.5, both released 2026-11-08) Severity: CVSS 8.8 — CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:H/A:H CVE: CVE-2026-124251 (Patchstack CNA, published 2026-11-10) — incomplete fix for CVE-2026-57766 Reporter: Greg Otto, via Patchstack Summary This technical report has been generated with the help of GLM-5.3-Flash. WPIDE’s 3.6.0 release attempted to remediate CVE-2026-57766 (unauthenticated CSRF, ≤ 3.5.6) by introducing a nonce check, but the check is scoped too narrowly: a security service validates the nonce only when the page URL parameter equals wpide exactly ( App/Services/Security/Security.php ). The plugin registers seven submenu pages whose slugs contain a #/ fragment — wpide#/file-manager, wpide#/file-editor, wpide#/image-editor, wpide#/db-manager, wpide#/config-manager, wpide#/snippets, wpide#/settings — so none match, and requests naming any submenu slug reach the plugin’s internal router with no CSRF validation. WordPress core accepts the URL-encoded #/ ( %23%2F ) in the page parameter, and core’s capability gate passes because the CSRF victim is by definition a logged-in administrator. The 3.6.2 release rebuilt the mechanism as an X-CSRF-Token header scheme but kept the same slug-scoped gate, so the bypass persisted.
