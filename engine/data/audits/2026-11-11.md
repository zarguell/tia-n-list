This is the 2026-09-16 gamefan class. It is not fixed because source/handle skips are policy, not in the fix license.
2. **16 published analysis files contain internal triage bookkeeping in their prose.** The lint flags them on every single run — 16 distinct files, ~224 warn instances today, 380 on 2026-11-06, 381 on 2026-11-09, so this is chronic, not a regression. Worst example, `fastapiadmin-authentication-bypass-cve-2026-111641.md` reads: *"…according to the event reference to radar.offseq.com. The event is the original mint for this new story… The new story is appropriate because no existing cluster covers this CVE."* That is the analysis agent narrating its own triage decision to the reader, on a live story page. The lint class is `(kept)`, so it warns and publishes anyway. Content quality, so not fixed here.
3. **Weakest of the sampled analyses is effectively contentless.** Same `fastapiadmin-…` file gives no CVSS, no affected-version range beyond "through version 30", no exploitation status, and cites a single aggregator (`radar.offseq.com`, itself a 64%-dropped source). ## Recommendations

1. **Skip the two flood entrants at the host and handle level.** Add `secquill.com` and `infonewscyber.fr` (plus `secquill@infosec.exchange`, `infonewscyber@infosec.exchange`) to the ingest skip list, or downgrade them to non-primary so their events can link but cannot mint scores. `radar.offseq.com`/`offseq@infosec.exchange` (64% dropped) and `github.com` (75% dropped) belong in the same review. Re-run the noise table after the change to confirm the FAIL clears.
2. **Promote the triage-bookkeeping lint from WARN to ERROR for newly written analyses**, and add an explicit "never narrate your own triage decision" line to the analysis prompt. Repairing the 16 existing files is editorial work and needs a separate pass; fixing the gate stops the bleeding at the source.
3. **Codify the rereport demote in `score.py`.** 53% of all digest overrides (67% today) exist to demote stories whose newest material restates an already-covered report with zero new CVEs, actors, victim counts or IOCs. `rereports`/`zero_delta` already exist in `score_breakdown`; a harder penalty for "appeared in a digest within the last N days AND newest event adds no new entity" would cut the daily override count roughly in half and free the digest agent for the actual editorial calls.
4. **Reconcile the Patch Tuesday count in one place.** The digest says 1,094, the slug and analysis say 1,093 and explain the discrepancy. Pin the number to the vendor total and let the analysis paragraph carry the "some outlets count 1,235/1,259" caveat. Minor, but it is the lead story.
5. **Watch the per-hour churn of `stories/*.json`.** Every scoring recompute rewrites `recency`/`peak_score` across the whole store: a single `ssg.py` invocation touched 264 files, almost all of them sub-1% recency drift, and the 14:03Z hourly then churned them all again. Not wrong, but it makes the git history unreadable and makes surgical audit commits (this one had to revert 259 files) fragile. Consider only rewriting a story file when a field changes by more than a threshold, or excluding `recency` from the committed payload.
