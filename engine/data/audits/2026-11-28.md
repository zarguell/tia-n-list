## Issues found

1. **Digest page renders the opening paragraph twice.** `engine/data/digests/2026-11-28.md`
   begins with the exact text of `2026-11-28.json`'s `summary`, and `ssg.py` renders both the
   summary deck and the body, so `/daily/2026-11-28/` shows the same 430-character paragraph
   back to back. Cause: the 11:34Z checker FAIL ("no coverage delta paragraph opening the
   digest") was cleared by prepending the summary text as a body paragraph. No other digest
   in the last 8 days does this (all open on `[NEW]`/`[UPDATE]`), so it is a per-run artifact,
   not a regression in ssg. Left unfixed: this is digest content, and editing published prose
   is not in the fix license.

## Recommendations

1. Decide where the digest's delta paragraph lives. Either (a) teach `ssg.py` to skip a
   leading body paragraph that is identical to `summary` before rendering `analysis_html`
   (three-line guard in the `daily/{d}/index.html` path, deterministic and testable), or
   (b) tighten the cronman checker/repair prompt in `cronman/lib/agent.py` so the repair
   writes a *new* delta paragraph instead of copying the summary. (a) is the durable fix
   because it also cleans up any future run that repeats the summary. This has now bitten the
   composer twice in spirit (Oct 4/5 logs carry the same "no coverage delta paragraph" FAIL
   text); the pattern is recurring enough to be worth a code fix.
2. Codify the dominant demote pattern in `engine/score.py`: single-source, count-only breach
   notices ("100,000 potentially impacted", "single-source single-event confirmation with no
   scope") are today 20 of 51 demotes and roughly the same share on prior days. A source-count
   and field-detail penalty applied below the digest gate would remove them from the override
   budget, leaving override slots for the genuinely under-ranked items the digest agent keeps
   having to rescue by hand.
3. 26 of 4068 shipped analyses now trip the prose-specificity lint (`stage=warn`, never
   quarantined), including today's DWP lead analysis, which names the subject but carries no
   CVE, IOC, or technique id. The count is stable (26 of 4066 yesterday), so nothing is
   rotting, but the warning fires every hour and is now noise. Either drop the warning for
   story-subject-only matches or accept it and stop logging it per-run.
4. `kevrichment/data/quarantine/` is untracked in the production checkout (one file,
   CVE-2026-115731 from 2026-11-18, 12K). Harmless but it will make every `git status` dirty
   and invites a stray `git add -A`; gitignore it or have the job commit/quarantine-clean it.
