CVE-2026-123158, dubbed *sshole, is a pre-authentication bypass in OpenSSH sshd when built against musl libc without PAM. On affected Alpine, OpenWrt, Buildroot, and Yocto systems, any password between 257 and 1,024 characters authenticates against accounts that have no password set, because musl crypt() returns a failure marker matching the locked shadow entry. Researcher Özgün Kültekin disclosed the flaw on November 5, 2026, the same day OpenSSH shipped version 10.6p2; the bug has been present since 2016, and glibc-based systems are not affected.

A successful attack gives a remote, unauthenticated login to accounts that should never accept a password, root, key-only deploy users, LDAP accounts, and default users on Alpine cloud images, with no prior access required. The exposed population is every internet-facing SSH service running on musl, a large share of containers and lightweight cloud hosts. This story matters more than a typical disclosure because the flaw lived silently for a decade and was patched on November 5 before broad reporting, so unpatched instances are already exposed and the window for quiet exploitation is wide.

Patch to OpenSSH 10.6p2 or later and restart sshd; Alpine published fixed packages on November 5, 2026. Where patching cannot happen immediately, set PasswordAuthentication no in sshd_config and restart sshd so only key-based logins succeed, and restrict SSH port 22 to trusted networks or a VPN. Hunt for successful password authentications in sshd logs against accounts whose shadow entry is locked, authentication payloads carrying passwords longer than 256 bytes, and repeated port 22 connection attempts from unexpected source IPs.

Watch for confirmed in-the-wild exploitation, a CISA KEV listing, and whether OpenWrt, Buildroot, and Yocto ship patched builds in step with Alpine. Any mass scanning of port 22 with overlong passwords, or exploit code in public repositories, would raise the assessment from patch-urgent to active incident.
