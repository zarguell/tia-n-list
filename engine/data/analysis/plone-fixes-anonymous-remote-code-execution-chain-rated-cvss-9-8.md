Plone's advisory 20261110, published 10 November 2026, closes a five-flaw chain that lets an anonymous visitor execute code on the server. The chain is not one bug but a stack of small ones: the conditional modifier classes in Products.CMFEditions declare no security, so methods such as edit are publishable and an unauthenticated caller can rewrite a modifier's TALES condition and run it; Products.CMFPlone, Products.MimetypesRegistry and plone.batching used allow_module too broadly, exposing imported names so restricted code reaches modules like os; and plone.restapi opened the standard library json module, letting json.dump and json.load call protected methods without the permission. The lead advisory carries CVSS 3.1 9.8 with CWE-862, four advisories are Critical and the restapi one Medium, no CVE had been assigned at publication and none of it is in CISA's KEV catalog. Remediation is a package bump to Products.CMFPlone 6.2.3, 6.1.6 or 6.0.16 with matched CMFEditions, MimetypesRegistry, plone.batching and restapi versions, or Products.PloneHotfix20261110 for anything from Plone 4.3 through 6.2 including Python 2.7 installs, followed by a restart of every Zope instance.

The exposure is worse than a CVSS 9.8 headline suggests because the entry point is an ordinary content tool rather than an admin endpoint. portal_modifier ships by default with CMFEditions, and Zope acquisition makes it reachable at any depth, so /folder/page/portal_modifier/ works as well as /portal_modifier/. That defeats the common mitigation of guarding one path prefix, and it made the 2 November pre-announcement, which asked operators to block portal_modifier before any technical detail existed, the most useful guidance anyone got for this flaw. Sites that patched cleanly still carry two problems. A changed modifier condition is stored in the database and survives the upgrade, so an attacker who touched a site before patch day keeps a foothold the new package version does not remove. And a site fixed through the hotfix package reports its old version string, so any scanner keyed on version numbers keeps listing it as vulnerable while the file-level fix is in place.

Operators who cannot take a release should install the hotfix, restart, then verify at @@check-modifier-conditions on the site root, which compares stored modifier conditions against the defaults and allows a revert; the hotfix itself logs POSSIBLE ATTACK: MODIFIED VERSIONING CONDITIONS FOUND on startup when a condition differs, and No changed modifier conditions found when it does not. A mismatch is not proof of compromise, since defaults drifted over the years and add-ons may legitimately change conditions, but an unrecognised condition should be treated as a compromise. Keep the portal_modifier block in the web server after patching, apply it at any path depth, and make sure the layer doing the matching actually decodes first: Apache, nginx and Traefik normalise percent-encoding before the rule fires, Varnish does not, so /%70ortal_modifier slips past a Varnish-only block. Expect fallout in custom code: Python Scripts and templates that imported names from Products.CMFPlone, Products.CMFPlone.utils, Products.CMFPlone.browser.navtree, OFS.ObjectManager, Products.MimetypesRegistry.common, plone.batching or json will now raise Unauthorized, and the sanctioned fix is a ModuleSecurityInfo declaration in your own add-on rather than another allow_module.

Two developments would move the assessment. First, CVE assignment and any appearance in KEV or an exploitation telemetry feed; the vendor requested numbers at release and none had been issued as of 11 November, and no scanning or exploitation activity has been published, so the current picture is a fully public, unauthenticated path to code execution with no observed use. Second, a working public exploit or proof of concept, which the vendor warned is likely given that all component detail is now public. Until either appears, the practical risk sits with internet-exposed Plone instances that have neither the hotfix nor a correctly placed portal_modifier block, and with the subset of those where an attacker already edited a modifier condition before patching.
