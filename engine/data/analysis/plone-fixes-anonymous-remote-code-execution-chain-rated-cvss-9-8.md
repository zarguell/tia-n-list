Plone has shipped a fix for an unauthenticated remote code execution chain rated CVSS 9.8. The remediation is a version bump to 6.2.3, 6.1.6 or 6.0.16 depending on release branch, or installation of a standalone Plone hotfix for operators who cannot take a point release immediately. The report available here does not carry CVE identifiers or the component-by-component breakdown of the chain, so the specific request path that reaches the vulnerable code is unconfirmed.

A 9.8 anonymous RCE in a CMS is a direct pre-authentication path to code execution on the web server, and Plone deployments tend to be public-facing by design. Government portals, university sites and Intranet-style installations that are reachable from the internet all fit the profile. The chain implies more than one flaw working together, which usually means the individual pieces look benign enough to survive earlier review, so a patch level alone may not be a reliable indicator of exposure across the stack of add-ons a given site runs.

Because the vendor offers a hotfix separate from a full release, the split matters for inventory. A site patched through the hotfix will not show the new version number, so version-based scanning will misreport it as vulnerable while the file-level fix is in place, and the reverse gap exists where an administrator applied neither. Audit on the hotfix presence and on the running Plone release together rather than trusting either signal alone.

For the near term, restrict administrative and content-management interfaces to known networks, keep reverse proxies from forwarding unauthenticated requests to Plone internals, and watch web logs for anomalous POST traffic against Plone view and traversal endpoints from unfamiliar sources. A vendor advisory with CVE numbers, any observed exploitation, and confirmation of which REST API paths are reachable anonymously would let defenders triage this properly instead of patching blind.
