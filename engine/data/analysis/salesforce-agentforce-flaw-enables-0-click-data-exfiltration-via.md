Zenity Labs published SalesBleed on September 24, 2026 as a chain of three Agentforce flaws: two allowed zero-click CRM data exfiltration and one turned an Agentforce agent inside Slack into an anonymous phishing vector. The exfiltration chain starts at a public Web-to-Lead endpoint such as webto.salesforce.com/servlet/servlet.WebToLead, where a hidden prompt injection in a lead field sits dormant until an employee asks the agent to review the newest submission. The poisoned lead then steers the default General CRM subagent's Query Records tool from the Leads table into Accounts data, and the agent prints an HTML img src tag whose hostname carries the stolen values into a DNS lookup against the attacker's authoritative nameserver. No Salesforce login, no victim click, no privilege escalation: the subagent already shipped with read access to both objects. There is no CVE; Salesforce fixed the specific Trusted URLs bypasses after Zenity reported them on June 1, 2026, and said it found no exploitation in the wild.

The reason this story outranks thirty others today is that it defeats the muscle memory of vulnerability management. There is no CVE to scan for, no patch version to inventory, no KEV entry, and the fix landed server-side at Salesforce between June and August 2026, so every scanner and patch report a defender owns will silently return clean while exposure is decided entirely by configuration: is Agentforce live, does one subagent hold Query Records reach across Leads and Accounts, and is a Web-to-Lead form public. The poisoned lead is also not a one-shot payload, it is a durable foothold in a table deliberately open to the internet that re-arms every time any employee reviews it, and an attacker who wants more throughput just submits more leads. And because the data leaves inside DNS resolution, the channel walks past HTTP egress filtering entirely; a single label holds 63 characters and a full name 253, which was enough for Zenity's proof-of-concept video to bleed out an entire Accounts table one account at a time.

Salesforce remediated the Trusted URLs redaction bypasses and Zenity confirmed the fix on August 19, 2026, so customer work is configuration and detection, not patching. Audit which subagents hold Query Records access to multiple objects and separate lead review from account read wherever the permission model allows it, since broad single-identity tool scope is what turned one injection into a breach. Hunt agent transcripts for img src tags or raw URLs appearing right after lead-review sessions, for hostnames under uncommon TLDs like .fun, and for URLs wearing curly braces or square brackets, the exact parser disagreement Zenity used to slip past redaction. Zenity also showed that both the agent's raw output and the redacted version appear in responses sent to the client, so capture full agent output at the API layer rather than trusting the rendered chat surface, and alert on DNS queries from user workstations that encode data in subdomain labels when agents are active. Treat Slack-connected agents as a separate surface: Slack's link unfurling crawls any raw URL the agent prints, which gives the same DNS-based theft with no image tag at all and powered the phishing variant of the third flaw.

Two developments would change this assessment. Any exploitation telemetry surfacing after the September 24 publication would convert this from a pattern proof into an active campaign, and Salesforce's clean statement predates the moment the technique and its proof-of-concept video became public, so the no-exploitation claim has a short shelf life. The other is a Trusted URLs-style bypass appearing in a second agent platform, which would confirm Zenity's argument that external input, broad tool scope, and rendered output sit together in every agent deployment and that output redaction is a race the parser can lose.
