GitLab's September 10, 2026 critical patch release shipped 19.3.2, 19.2.6, and 19.1.8 to close CVE-2026-85706, a CVSS 10.0 path traversal (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:N) in the repository commits API of self-managed Community and Enterprise Editions. Improper path confinement combined with missing authentication enforcement lets an unauthenticated attacker read arbitrary files on the server with a single HTTP request. The vendor advisory stretches exposure back to 18.7 before 18.11.12 and 19.0 before 19.0.9, older branches than most coverage mentioned. Researcher s3ntago disclosed it through HackerOne, and the same release fixed CVE-2026-87719, a CVSS 9.9 EE deserialization flaw where any authenticated Duo Chat user can pull Advanced Search configurations and credentials, plus CVE-2026-88765, a CVSS 8.5 authenticated RCE in Advanced Search indexing.

A pre-auth file read on a CI/CD control plane is not a data exposure footnote; it is a key extraction primitive. The readable paths hold gitlab.yml, CI/CD variables, deployment tokens, and private keys, which is why both CISA and watchTowr describe account compromise, cloud access, source code theft, and lateral movement into CI/CD as the follow-on path. The 2023 precedent CVE-2023-2825 required a public project nested five groups deep on a single affected version; this flaw needs any one public project, and unpatched code reaches back to the 18.7 line. Censys counts more than 86,000 internet-facing GitLab hosts against a platform GitLab says runs on over half the Fortune 100, and the gap from patch release to CISA KEV listing was roughly one day, with watchTowr seeing probes by 06:00 UTC on September 11. That arithmetic makes slow patch cycles the losing side by default, and it carries a corollary the coverage leaves implicit: patching closes the read without revoking anything already read, so any internet-facing instance that ran unpatched after September 11 should be treated as a secrets breach, not merely an outdated server.

Upgrade every self-managed instance to 19.3.2, 19.2.6, or 19.1.8 now, and note that 19.1 exits support on September 17, so 19.1.8 is a dead-end patch that needs a planned next hop. Hunt access logs for HTTP POST requests to /api/v4/projects/{id}/repository/commits/ URIs carrying file.path parameters, the watchTowr exploitation signature, and deploy the three detections GitLab published alongside the advisory: LFI attempt reading gitlab.yml, LFI via metadata.path parameter, and LFI file path attempt. Prioritize internet-facing instances with at least one public project, watchTowr's stated prerequisite for the observed attack path. Where logs show hits, rotate everything the GitLab service account can read: CI/CD variables, deploy tokens, runner registration tokens, and credentials referenced in gitlab.yml.

Two developments would change this assessment. OffSec has already published an exploitation analysis and watchTowr expects indiscriminate exploitation to follow the probing, so the first confirmed mass-scanner traffic or mature public PoC moves this from urgent patching to incident response. The second is a demonstrated chain from this file read to code execution, which would turn rotate-and-patch into rebuild, and exploitation hits against instances with no public projects would falsify the stated precondition and widen the exposure math considerably.
