Apify, a Czech web scraping and browser automation platform, disclosed that an unauthorized third party used a compromised credential on 9 and 10 November 2026 to obtain account credentials and access related Apify accounts. The intrusion was detected on 11 November at 12:13 UTC, after which Apify cut off access and reported no further attacker activity since 11 November. The company has not published CVEs or a root cause; the access path was closed and the incident remains under investigation, with a post-mortem promised.

The exposure is not limited to Apify's own console. The breach notification sent to affected customers references user PII, authentication data including hashed passwords and 2FA recovery material, and payout details, while Apify simultaneously states it found no indication that account data stored on the platform was affected. That gap matters: customers who did not receive a notice cannot verify whether their data was touched, and any credential that touched Apify during the window should be treated as suspect. With roughly 80,000 customers, including Microsoft, Samsung, T-Mobile, Accenture, Siemens, the European Commission, and Roche, and with Apify sitting in the data-collection layer for downstream pipelines, a compromised internal credential is a supply-chain problem rather than an isolated vendor incident. The practical risk is credential reuse and unauthorized access to customer storages and connected repositories, not only direct data theft.

Defenders should rotate every Apify API token and Apify Proxy password, reset active sessions and 2FA, and reconnect GitHub integrations through the Actor console (Change provider, then GitHub, authorizing once per account and organization). Restrict storage access in the Apify Console under Settings, General resource access, set to Restricted, because while a storage is open anyone who knows its storage ID can read it. Hunt for unexpected new API token usage, OAuth reconnections, and access to storage IDs during 9 to 11 November 2026. Apify states API tokens are now stored only as hashes and that network restrictions between internal services and stronger internal authentication were added, but no log paths or telemetry field names have been published, so detection must rely on Apify-side audit trails and your own token-usage baselines.

Watch for the promised post-mortem to establish the root cause, the actual scope of accounts and data types exposed, and whether the revoked OAuth connections were precautionary or confirmed exposure. Also watch for any reuse of rotated Apify credentials in downstream systems and for phishing that reuses breach-notification language, since Apify has warned it will never ask for passwords, 2FA codes, or payment details.
