Zeabur disclosed a second breach in two months: on October 14-15, 2026 an attacker used leaked internal credentials stored in plaintext to enter shared clusters across nine regions, some Dedicated Servers, and internal systems, then read the platform database. The credentials included cluster admin tokens with no expiry created in January 2024 that were never rotated after the August incident, plus AWS and GCP keys, while admin portals remained reachable from the public internet. The breach touched 321,810 accounts and roughly 3.2 million environment-variable records, with root sign-ins on 101 GCP servers, SSH keys added to 50 of them, and 16 customer disk copies attached to attacker VMs. The likely source of the leaked credentials is the August 2026 incident, when an attacker exploited CVE-2026-7644 in a customer's NextChat v2.16.1 service and moved laterally through poorly isolated shared-cluster networks to AWS root and the production database, but Zeabur has not confirmed the link.

The exposure is not just account metadata: environment variables commonly hold third-party API keys, cloud credentials, database passwords, and signing keys, so a platform-database read of 3.2 million records is a downstream compromise of every service those tenants run, with AI service keys a stated attacker target. The blast radius extends to 865 database containers where commands ran and to compromised GCP hosts, and variables that tenants migrated to their own servers after August escaped the database read but remain at risk on any compromised host. The reason this story matters more than a routine breach note is that the second incident was enabled by the first: Zeabur rotated credentials in August but left the admin tokens and public admin surface untouched, turning a contained August intrusion into a full platform collapse two months later. Anyone who ever stored a live secret in Zeabur should treat it as leaked, including credentials already rotated after August.

Zeabur's response guidance is to rotate every credential stored in Zeabur environment variables (API keys, cloud keys, database passwords, signing and encryption keys), revoke old keys with providers first, then redeploy; recreate all platform Access Tokens; and for GCP Dedicated Server users rebuild affected hosts from backups and reset root passwords, removing unfamiliar SSH keys, crontab entries, systemd services, and k3s workloads. Variables migrated to a tenant's own Dedicated Server are outside the platform-database read but still need rotation if the host was among the 101 compromised GCP servers. Hunt for attacker activity using the IoCs Zeabur published: root sign-ins on GCP servers between September 1 and October 15, SSH keys added by the attacker, external callbacks from planted programs in PostgreSQL containers, and Zeabur GitHub App actions between October 15 15:05 and 18:54 UTC. Service owners should also review provider usage and billing from October 14 onward, and from September 1 for GCP Dedicated Server tenants.

The assessment changes on three developments: confirmation or refutation of the link between the August credential leak and the October breach; the final scope of the 865 container reads and the 101 compromised hosts as Zeabur completes its investigation; and whether any of the leaked GitHub App or cloud keys were actually abused before rotation, since GitHub audit logs were still pending. Zeabur's wind-down runs to December 31, 2026, with shared clusters pausing December 1, so tenants have a bounded window to migrate and verify.
