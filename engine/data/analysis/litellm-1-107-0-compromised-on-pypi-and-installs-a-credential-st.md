On October 21, 2026 the LiteLLM project's PyPI release pipeline was compromised and version 1.107.0 was published carrying a credential stealer and backdoor. Attackers used stolen GitHub CLI OAuth tokens from three LiteLLM engineers to disable branch protections, merge a change pointing the releaser at a different source repository, and run a compromised workflow that signed and published poisoned artifacts. The malicious wheels were live on PyPI from 11:39 to 13:23 UTC and affected Docker Hub tags until 14:20 UTC, with an estimated 49,000-plus downloads during the window. Because the payload used Python startup hooks in files such as cook.pth, cook.py, and sitecustomize.py, it ran whenever an interpreter started, even if the application never imported LiteLLM. Multiple security firms detected the attack within six minutes of publication.

The compromise had a longer lead-up. Malicious workflows ran inside the BerriAI/litellm repository on October 10 and October 12, 2026, eleven days before the poisoned release. The root cause appears to be an innocuously named internal user account exposed to the public internet, whose GitHub CLI tokens were likely leaked by Claude Code embedding them in response bodies that were logged to LiteLLM logs. Attackers then had access to three sets of developer credentials and used them to push the release through the official pipeline. LiteLLM has 61,800 GitHub stars and roughly 92 million monthly PyPI downloads and is used by companies such as NVIDIA, Netflix, AT&T, and Okta, so the blast radius was large even though private enterprise customers were not impacted.

Microsoft's analysis found two execution paths, a credential collector launched through a path extension and a Unix-oriented loader persisted through site-specific configuration, targeting authentication material across developer tools, AI applications, cloud environments, browsers, and infrastructure. A separate module attempted to read credential and model-configuration records from the LiteLLM proxy database. The LiteLLM team's own post-mortem traced the backdoor to a single GET request against an agent-listing endpoint and a master key exposed in May that was never revoked.

Response should assume compromise on any host that ran the affected version. Organizations must not start Python or pip inside a suspect environment to check for the package, because that would trigger the collector. Instead they should inspect filesystem artifacts and network telemetry, rotate all cloud keys, AI provider secrets, and proxy database credentials, and audit any outbound connections from the exposure window. Private enterprise deployments were reportedly unaffected, but any host that pulled litellm 1.107.0 from PyPI or Docker during the exposure window should be treated as compromised.
