CVE-2026-105445 was a flaw in Docker Hub's account-to-organization conversion. From August 26, 2024, converting a personal account also reassigned its personal access tokens to whatever existing user the converter named as the new organization's owner: the token's owner record changed, the secret never rotated, and no consent or notification was requested. An attacker could create an account, mint a PAT, convert, and name a victim, ending up with a live credential that authenticated to the registry as that victim and carried the victim's org memberships. Peter Molnar and Krisztian Hozak of mptrdev.com, publishing the details as GhostPat, reproduced it twice on September 28 and 29, 2026; Docker fixed production the same afternoon the report arrived, under four hours end to end, and its audit of every conversion in the window plus roughly 304,000 pushes made with transferred tokens found no evidence of exploitation.

The headline frames this as image tampering, but the read half is the sharper risk: the researchers confirmed the minted token could pull the target's private repositories, so the quiet version of this attack is not poisoning at all, it is exfiltration of whatever private images the victim can read, internal build details and baked-in credentials in tow. And "no evidence of exploitation" is narrower than it sounds: Docker itself notes registry logs show when a token was used, not that it existed, so a transferred PAT created and never used leaves no trace, and the October 8 force-deactivation carried an opt-out, so some transferred tokens may have outlived the cleanup. The exposed set is small and self-identifying: Docker emailed only users whose accounts received transferred tokens, on October 2, so absence of that mail means no exposure. The story still matters because the root cause is a missing consent step in the identity layer of the default registry, exactly the class of design flaw that tends to repeat across other flows.

If the October 2 email with the subject line "Docker Hub Vulnerability Identified & Resolved" reached anyone on your team, treat every token it lists as compromised until re-issued; that mail names in-scope tokens by description and creation date. Regardless, audit Account settings, then Personal access tokens, on every Hub account your team controls and revoke anything unneeded, judging by creation date rather than name, since a minted token's name is attacker-chosen and a familiar-looking name proves nothing. Check the account switcher for organizations nobody remembers joining, the second trace the technique leaves, and prefer organization access tokens over personal PATs for shared automation. In your own registry telemetry, the specific hunt is one credential authenticating under more than one identity, plus bearer exchanges against `POST /v2/auth/token` from unfamiliar clients.

Two developments would move this assessment. The first is Docker's structural follow-through: it has promised consent before a user can be named an organization owner, an auditable history of token ownership changes, and a review of other credential-ownership flows for the same pattern, and any slippage or second finding there widens the blast radius. The second is whether the same conversion-reassigns-credentials pattern exists in other registries such as GHCR, Quay, or GitLab's, which would turn a Docker incident into a registry-design class. Confirmation of the researchers' unconfirmed worst case, that official `library/` images are publishable through the same path from a plain account, would put the severity far above anything currently scored.
