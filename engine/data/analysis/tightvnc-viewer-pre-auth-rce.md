TightVNC Viewer contains a pre-authentication remote code execution vulnerability triggered by a malicious server. The server announces a crafted 32768 by 32769 framebuffer at 32 bits per pixel, causing the framebuffer size calculation to overflow and wrap down to a 128 KB allocation while the viewer continues using the original, much larger dimensions when calculating pixel writes. The result is a server-controlled out-of-bounds write in the viewer, a memory-corruption primitive arising from an integer overflow where different parts of the application disagree about the true buffer size. SSD Disclosure published the research.

The practical exposure is anyone using TightVNC Viewer to connect to an untrusted or attacker-controlled VNC server, since exploitation requires no authentication and the malicious party is the server rather than the client. The flaw is a good example of how a small integer-overflow mistake becomes a powerful primitive when allocation and access paths use inconsistent size values.

What to watch: whether TightVNC publishes a patched release and advisory, and whether other VNC viewers share the same framebuffer calculation. Users should avoid connecting TightVNC Viewer to untrusted servers until a fix is available and verify the source of any VNC server they connect to.
