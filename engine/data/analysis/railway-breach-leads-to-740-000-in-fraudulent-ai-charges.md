Railway, a developer platform-as-a-service, closed the book on its October intrusion with an incident report that starts at 07:28 UTC on October 20, 2026: an attacker exploited a previously unknown vulnerability in Railway's build infrastructure to partially escape filesystem isolation on a shared build VM and read host files. From there they took an internal credential, pulled build histories and a copy of Railway's internal source code, and then abused an improperly configured trust relationship to reach the credentials that decrypt customer environment variables. Railway evicted them roughly 26 hours later, with its preliminary report fixing the window at October 20 13:58 UTC to October 22 03:32 UTC. The company puts the ceiling at 1.85% of workspaces, about 100,000, and stresses that this is the maximum potentially exposed rather than a confirmed theft count. Stolen customer secrets funded approximately $740,000 in fraudulent AI usage.

The $740,000 is the least of it, and reading this as a billing anomaly undersells what the chain actually produced. Railway's build infrastructure decrypts customer environment variables as part of normal operation, so escaping isolation on a build VM does not expose files so much as it converts a build tenant into a credential store; the trust misconfiguration, not the sandbox escape, is what turns a partial break into platform-wide exposure. Every workspace that held a long-lived secret before October 21 is therefore in scope whether or not it was notified, because Railway's notification criteria select workspaces by risk, not by confirmed access. Source code theft matters for the same reason: the attacker learned exactly how decryption worked, so defenders should assume cloud account keys, database passwords, and private registry credentials were reachable, not just the subset that happened to be spent on AI inference.

Rotate rather than review. Revoke and reapply every sensitive environment variable stored on Railway before October 21, 2026, starting with cloud provider keys, database passwords, and registry tokens, and treat values that were merely encrypted at rest as disclosed. Check AI provider key-usage and billing dashboards for requests from keys you did not create, since that is precisely how the $740,000 was drawn, then check cloud audit logs for API calls from unfamiliar addresses in the days following October 20. Inside Railway, look for builds or deployments from repositories you do not recognize, environment variable reads in build logs, and workspace deploy history that changed inside the October 20 13:58 UTC to October 22 03:32 UTC window. Railway says every exploited vector is closed, but any secret mirrored into another CI system is already burned, so rotate there as well.

Two developments would widen the assessment. First, Railway naming the actor and publishing a confirmed-compromised workspace count instead of the 1.85% ceiling would replace inference with a number defenders can scope against. Second, evidence that the stolen cloud keys were used beyond AI billing, such as new cloud accounts, mining workloads, or lateral movement into customer infrastructure, would make this a supply-chain credential event rather than a contained platform incident. Watch also for whether other build-and-deploy platforms that decrypt secrets in shared build infrastructure get audited on the same pattern.
