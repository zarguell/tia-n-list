Microsoft 365 device-code phishing does not break authentication; it borrows it. An attacker starts an OAuth 2.0 Device Authorization Grant with a client they control, plants the short code in a lure, and the victim pastes it at microsoft.com/devicelogin, where they complete the tenant's own MFA and Microsoft hands access and refresh tokens to the attacker's client. The November 19 cluster wraps that flow in PDFs styled as SharePoint payment and invoice documents, sometimes with a single-period subject and almost no body, and Group-IB's October 29 MadApe research ties the pattern to 155 root domains with device-code components on 97 of them. On November 17 Microsoft used GitHub Copilot CLI to show the same approval problem for coding agents: a phished device code can yield remote steering of an active session, poisoned Copilot Memory entries, cloud-synced sessions and private repo access, all lab outcomes and not observed in the wild.

That makes this more than another credential-theft item. A successful approval is an authenticated session: the CSA note counts 340 or more Microsoft 365 organizations hit by the related EvilTokens campaign across five countries by mid-March, and Group-IB says its domain figures count infrastructure rather than victims, so neither number should be read as a confirmed compromise count, but both show a supply chain of reusable kits. Password resets and FIDO2 or passkey origin checks do not evict a token the victim legitimately authorized, and the same approval habit now reaches mailboxes and developer workstations, where the Copilot CLI scope set repo, read:user, read:org, gist and codespace can expose source and infrastructure definitions. The event list gives no victim count for the November 19 campaign, which is exactly why the desk should say what is at stake: MFA completion by the victim is the bypass, and a fake SharePoint document is enough to trigger it.

There is no patch version to chase, so the fix is configuration and hunting. Inventory legitimate device flow use, then set an Entra Conditional Access Authentication Flows policy to block Device Code Flow in report-only mode before enforcement; Microsoft and Group-IB both recommend that block, with Microsoft advising temporary disabling of the account alongside revokeSignInSessions during containment because access tokens can remain live for about an hour. Hunt 90 days of Entra sign-in logs for authenticationProtocol: deviceCode and originalTransferMethod: deviceCodeFlow, then correlate with PDF link clicks, new inbox rules, new OAuth grants and devices registered soon after the approval; also look for /api/device/start requests, the X-Antibot-Token header and python-requests/2.25.1 polling. On the GitHub side, review GitHub Enterprise audit fields application_name, token_scopes and actor_ip for Copilot authorizations carrying repo, read:org, gist or codespace, revoke unexpected grants, and review Copilot Memory and cloud session settings.

The assessment changes if Microsoft or GitHub reports the Copilot CLI lab outcomes in real intrusions, especially remote steering or Memory poisoning following an unsolicited approval, because that would move the agent risk from theoretical to incident-driven. It also changes if hidden-relay kits spread: KnowBe4's August 2026 sample ran the device grant without ever displaying the code, which defeats user training that tells people to reject only codes they see. Watch whether the MadApe and Wazza domains are disrupted or rotated, since 133 of Group-IB's 2026 domains used one registrar and infrastructure concentration is the clearest disruption target.
