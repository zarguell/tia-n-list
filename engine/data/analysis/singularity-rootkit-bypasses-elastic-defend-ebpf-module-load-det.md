Security researcher matheuzsecurity documented a technique where the Singularity Linux rootkit evades Elastic Defend by abusing the product's trusted_pids eBPF map. Elastic Defend monitors Linux kernel module loads via a BPF-based module_load event, introduced around version 8.14 and enhanced in 9.5.0 with a taint_flags field. The rootkit loader dynamically identifies the relevant Elastic BPF program and map, then adds its own process ID to the trusted_pids hash. When the BPF program checks whether the loading process is trusted, it finds a match and exits before collecting module metadata or generating telemetry.

The proof of concept was tested against Elastic Defend 9.5.2 on Ubuntu with kernel 6.8.0-138-generic. The technique suppresses the "Kernel Module Loaded with Tainting Flags" EQL rule that Elastic introduced to detect unsigned or externally built modules. Rather than relying on a fixed map identifier, the rootkit dynamically locates the map at runtime, which means the evasion adapts across Elastic versions without hardcoding offsets.

This is significant for defenders running Elastic's endpoint agent on Linux. The trusted-process exclusion model creates an attack surface: if a rootkit can inject itself into the trusted_pids map, all subsequent module loads go unmonitored. Elastic's EQL detections for tainted modules become ineffective against this class of evasion. Organizations should monitor for unexpected eBPF map modifications and consider supplementing Elastic Defend with kernel integrity monitoring that does not rely on the same BPF infrastructure.
