Flare analyzed underground forum traffic and found eBPF rootkits moving from conference talks into practical, tutorialized tooling. One Russian-language forum post walked through building an implant that hides processes and activates only on a specific packet, with screenshots the author presented as working demonstrations. Other posts shared rootkit code directly. The target is the same Linux estate that runs most production servers, and the tooling is being handed to actors who previously could not assemble it.

The technical shift is what gives this weight. Classic Linux rootkits load a kernel module to hook syscalls, and because module loads are well understood, most EDR products alert on them and a routine `lsmod` reveals them. eBPF programs use the kernel's own sanctioned `bpf()` interface, the same one Cilium, observability agents, and legitimate security tooling depend on, and they load without a module. An implant can hook kernel functions, observe syscalls, and inspect or rewrite network traffic while leaving no entry in `lsmod`. Existing detection that keys on module loads, including the detections built for the earlier wave of eBPF rootkits such as the Singularity-style loaders, does not transfer cleanly to this generation.

The practical detection problem Flare describes is attribution: once a program is loaded, the host does not readily reveal who loaded it or what it does. Defenders should treat loaded BPF programs and their pinning state as first-class inventory, alert on BPF program loads by non-orchestration processes, and baseline which Cilium or observability programs are supposed to exist on each node so an extra one stands out. Network-side anomalies are still useful because packet-triggered activation implies traffic to an unusual destination.

What to watch is whether these forum tutorials produce named malware families in the wild, and whether the major Linux EDR vendors ship detections for BPF program loads rather than only for kernel modules. BleepingComputer's write-up is a summary of Flare's research and carries no victim counts, CVE, or indicators, so the current claim is capability diffusion, not an active campaign.
