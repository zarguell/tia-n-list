Researchers at the Institute of Information Security, Graz University of Technology, present File Notification Attacks at ACM CCS 2026 in The Hague, and the mechanism is permission bypass at the notification layer, not a memory bug. The file-event APIs built into every major OS, Linux inotify since kernel 2.6.13 in 2005, Android FileObserver since 2008, Windows ReadDirectoryChangesW since Windows 2000, and macOS File System Events since 10.5 in 2007, report opens, writes, moves, and deletions for files a process cannot read, provided it holds read permission on the parent directory. The Linux case is tracked as CVE-2025-68788. File contents are never needed; event names and timing carry the signal. The researchers state they are unaware of in-the-wild exploitation, and every attack shown requires a local cross-user foothold or a supply-chain-compromised package.

The unified claim goes past any single platform quirk: for roughly two decades, metadata permission boundaries have been broken at the OS layer, so any unprivileged local process doubles as a behavior sensor. On shared Linux hosts, an inotify watch on /dev/input or /dev/pts leaks cross-user inter-keystroke timing over SSH, and two decades of timing-attack literature say that reconstructs typed content. On Android, FileObserver bypasses the FUSE per-app storage view, so an app with zero permissions observes WhatsApp's private folder at /sdcard/Android/media/com.whatsapp/WhatsApp and receives MOVED_TO events with filenames, a timeline of which media arrived, was sent, or was deleted. On Windows, a watch on C:\ reports full paths system-wide regardless of ACLs, and Firefox's per-site storage directories yield real-time identification of visited websites among the top 1000 at a 97.8 percent F1 score. Exposure is effectively the entire installed base because the only near-complete fixes are missing or shipped disabled, which makes this a reusable surveillance primitive for any infostealer-grade implant rather than one vulnerability awaiting a patch.

Defender actions differ per platform and most are configuration, not patching. On Linux, run inotifywait -m -e access,modify /dev/input; no output on keypress means the kernel carries the fix, shipped in 5.10.248, 5.15.198, 6.1.160, 6.6.120, 6.12.65, and 6.18.3, and note the mitigation is partial since utimensat() still generates parent events. On Windows, the fix documented April 8, 2025 in KB5058189 against CVE-2025-21197 and CVE-2025-27738 sits behind the EnforceDirectoryChangeNotificationPermissionCheck value, default 0; set it to 1 under HKLM\SYSTEM\CurrentControlSet\Policies or Control\FileSystem, and hunt for unusual processes holding handles on volume roots and calling ReadDirectoryChangesW, including dotnet FileSystemWatcher consumers. On Android, where no fix exists, look in logcat for apps without storage permissions registering FileObserver watches on /sdcard/Android/media paths and emitting MOVED_TO lines with filenames. On KDE Plasma under Wayland, a watch on /usr/bin/pkexec telegraphs the polkit prompt and lets a fake dialog cover it; force the password window to Keep Above Other Windows, since KDE states focus-stealing prevention is not a security mechanism and SteamOS ships Plasma 6 too.

Two developments would move this assessment. A follow-up kernel fix closing the utimensat() residual, or a new CVE superseding CVE-2025-68788, would upgrade Linux from partially mitigated to patched and put Windows as the softest target. Absent that, watch for Microsoft flipping the registry default in a general update, Android shipping a FUSE-layer fix for FileObserver, or these primitives surfacing in malware tooling, any of which would confirm the transition from academic demonstration to commodity tradecraft.
