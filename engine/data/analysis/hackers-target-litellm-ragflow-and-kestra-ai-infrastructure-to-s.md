Microsoft Threat Intelligence documented three real intrusions, not proofs of concept: a LiteLLM gateway, a RAGFlow deployment, and a Kestra workflow environment, each ending in credential theft and persistence, with XMRig mining on LiteLLM and Kestra (v6.26.0 against a Monero pool) but not RAGFlow. In the LiteLLM case Microsoft assesses initial access through the public chain of CVE-2026-42271, command execution in the POST /mcp-rest/test/connection and /mcp-rest/test/tools/list endpoints of LiteLLM 1.74.2 through 1.83.6, and CVE-2026-48710, the Starlette BadHost host-header bypass affecting Starlette 1.0.0 and older, which strips the authentication gate entirely. The payload then read /proc/1/environ for provider keys and the master key, dumped the LiteLLM_VerificationToken and LiteLLM_ProxyModelTable tables from an Azure PostgreSQL backend using the harvested DATABASE_URL, wrote an SSH key to a service account, flagged payload directories with chattr +i, and ran XMRig with RandomX msr tuning. The Kestra intrusion is assessed as exploitation of CVE-2026-49869, a critical authentication bypass leading to workflow-origin bash execution and Docker socket enumeration; the RAGFlow case began with SSRF-style probing and ended with a monkey-patched TenantLLM.insert() capturing OpenAI, Azure, Anthropic, and Gemini keys on every new LLM configuration.

The argument to take from this is that a compromised AI gateway is a secrets breach with a compute bill attached: one exposed LiteLLM host yielded provider API keys, the master key, proxy-issued virtual keys, UI credentials, and the database connection string, so the blast radius covers every application routing through the proxy and every provider account those keys can spend. None of the tooling was novel. The LiteLLM advisory published April 21, Horizon3's unauthenticated chain writeup landed June 1, OSTIF's May 26 BadHost disclosure warned the flaw reaches FastAPI, vLLM, LiteLLM, and most OpenAI shim proxies, and CISA added CVE-2026-42271 to the KEV catalog on June 8, so the wave arrived roughly two to four months after public warning. Shared scanning node 45.150.109.151 appears in the telemetry across multiple targeted AI workloads, pointing to opportunistic scanning of internet-exposed management surfaces rather than bespoke targeting. Kestra's own June 3 advisory, GHSA-2q47-568g-9h4f (CVE-2026-53576, Critical 10.0), documents the same failure class reaching root: an anonymous caller creates and runs a workflow with a Process runner shell task in default deployments that mount /var/run/docker.sock, the exact access pattern Microsoft describes in this intrusion.

Patch LiteLLM to 1.83.7 or later and Starlette to 1.0.1 or later, or block POST /mcp-rest/test/connection and /mcp-rest/test/tools/list at the reverse proxy; move Kestra to 1.3.21 or 1.0.45 or newer and stop mounting docker.sock into orchestration containers. Keep gateway, retrieval, and workflow management surfaces off the internet, put the PostgreSQL tier behind a private endpoint, and rotate provider keys, the master key, virtual keys, and DATABASE_URL credentials for anything that was reachable. Hunt on the published telemetry: gateway ancestry (litellm, ragflow, kestra parent processes) spawning bash, python3, curl, or wget; command lines touching /proc/1/environ, LiteLLM_VerificationToken, or psycopg2; modprobe msr allow_writes; crontab rewrites, authorized_keys appends, and chattr +i. Network pivots: yosemite[.]jp, gobygo[.]net, oast[.]me, 45.150.109.151.sslip.io, raw-IP beacons on port 81, mining pool auto.c3pool[.]org:443, and the C2 pairs 135.125.10[.]56:19888 and 172.232.38[.]92:32991. Blockable file hashes include the /tmp/d ELF f64b88e9318bdf23f2dd119a0ce1dd1bdb3c8cd2e0e1e23ba3ef2e19072b79cc, XMRig samples 49fdcf32bfe837899a84e8938f0d07ae96ddd218a280a09eb60df8d64597bd8f and 3af9f25a4d45bb4f1ec5627cdbc6703cf3b4be75a892162d299d80ddfb266f42, and bridge installer 3d24ac736635e0fa0c5c459c9e18ca09d1ec9a1751a4503130934395609bd7e0.

Two developments would change this assessment. CISA adding CVE-2026-49869 or the RAGFlow candidates (CVE-2026-45312, CVE-2026-28797, CVE-2026-24770, CVE-2025-68700) to the KEV catalog would confirm the wave widened beyond LiteLLM into retrieval and orchestration tiers. A confirmed CVE assignment for the RAGFlow execution path also matters, since Microsoft states only low confidence on which flaw enabled code execution there; pinning the sink would turn the observed SSRF-then-RCE sequence, days apart against the same service, into a signature defenders can actually scan for.
