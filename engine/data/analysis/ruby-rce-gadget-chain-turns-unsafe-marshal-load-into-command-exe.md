Security firm elttam published a universal deserialization gadget chain that turns a single unsafe Marshal.load call into remote command execution on Ruby 4.0.6. The chain reportedly works unchanged on Ruby versions as far back as 3.3, which matters because earlier proofs of concept broke after changes in Ruby 3.4. No CVE is assigned; the risk is the API itself.

The chain starts by referencing Gem::SpecFetcher, which triggers RubyGems autoloading and pulls additional classes into an otherwise minimal Ruby process. It then combines retrieval of attacker-controlled content with evaluation of that content as Ruby code, relying on Ruby's object reconstruction during deserialization. The research builds on over a decade of Ruby deserialization exploitation, including prior chains against Rails, YAML.load, and RubyGems.

The exposure is narrow but dangerous: any application that passes untrusted data to Marshal.load is remotely exploitable, and Ruby's native serialization format gives no easy way to distinguish malicious payloads from legitimate ones. Watch for follow-up tooling that wraps the chain into Metasploit or exploit kits, and audit code paths that deserialize data from network input or storage. There is no patch to apply, only code changes to avoid Marshal on untrusted data.
