An attacker used compromised IAM credentials for AWS account 805246085872, the account Qubole's platform uses, to assume cross-account roles that customers still trusted, between October 14 and October 26, 2026. Every request carried an External ID and every one succeeded, because the roles remained in place long after companies stopped using Qubole and could read nearly all of the data the attacker targeted. The activity came from a rented OVH server and the Mullvad VPN, and none of it originated from Qubole's network. Role session names followed a consistent quiam- prefix with a suffix describing the action taken. Qubole is a cloud data processing platform owned by Idera.

The victim set is larger than the organizations actively using Qubole. Any account that ever integrated the platform and left the role in place was exposed, and Sentra counted more than a dozen organizations hacked in a single attack, with dozens of Qubole customers impacted and about 100 passwords and keys read in seven minutes. The actor made zero write actions, so nothing was changed or deleted, only stolen, which is why the activity stayed quiet. The External ID is not a secret: Wiz notes it is logged in plaintext in CloudTrail, so possession of the vendor credential plus the External ID is enough to assume the role. The actor enumerated resources, harvested secrets from Lambda environment variables, Secrets Manager and SSM Parameter Store, validated credentials with TruffleHog against AWS, Entra ID and Okta, and exfiltrated S3 data, sometimes downloading entire buckets in one session. That means the blast radius extends past S3 data into identity providers.

Treat this as configuration remediation, not a patch. Review CloudTrail from October 1, 2026 onward in every account holding an integration role, for AssumeRole events where userIdentity.accountId is 805246085872 and sourceIPAddress is not an AWS address, and for role session names beginning with quiam-. Enable S3 data events in CloudTrail or S3 server access logs, because management events do not record the object reads that make up the exfiltration. Rotate every secret, parameter and Lambda environment variable the role could read, and revoke active sessions for the role. Remove unused Qubole roles or restrict their trust policies, and add a source IP condition that limits assumption to Qubole's documented network ranges; Wiz states a source IP condition alone would have blocked every role assumption it observed.

Two developments would change the assessment. First, any disclosure of how the Qubole account credentials were obtained, since that determines whether the same access path exists for other vendor integrations. Second, The Register notes a separate October 8-11 campaign using customer-owned AWS access keys, which suggests the actor was working multiple trust paths at the same time.
