Qubole, a data-lake platform owned by Idera, reaches customer AWS accounts through cross-account IAM roles that customers create and trust. An attacker who obtained credentials for AWS account 805246085872, the account Qubole's platform uses, called AssumeRole against those customer roles between October 14 and October 26, 2026. Every request carried an External ID and every one succeeded, because the roles were still trusted even where Qubole had been dormant since the spring. The first observed activity came October 14 from a Mullvad VPN address, 45.83.220[.]211, using IAM user AIDA3W7DIFLYOLTK63SFS; from October 15 most traffic came from an OVH VPS, 57.129.54[.]120, and from October 18 a second IAM user, AIDAJYRRH5Y3A7AAJM2HW, appeared with another Mullvad address, 185.209.199[.]73. Role sessions were named quiam-enum and quiam-scope-full. No CVE tracks this; it is a trust and credential problem.

The victim set is larger than the organizations actively using Qubole. Any account that ever integrated the platform and left the role in place was exposed, and Sentra counted more than a dozen organizations hacked in a single attack, with dozens of Qubole customers impacted and about 100 passwords and keys read in seven minutes. The actor made zero write actions, so nothing was changed or deleted, only stolen, which is why the activity stayed quiet. The part the event list does not spell out is that the External ID is not a secret: Wiz notes it is logged in plaintext in CloudTrail, so possession of the vendor credential plus the External ID is enough to assume the role. The actor also validated victim credentials with TruffleHog against AWS, Entra ID and Okta, meaning the blast radius extends past S3 data into identity providers. That is why this story outranks most of today's feed: the weakness is standing vendor trust, which no patch closes.

Treat this as configuration remediation, not a patch. Review CloudTrail from October 1, 2026 onward in every account holding an integration role, for AssumeRole events where userIdentity.accountId is 805246085872 and sourceIPAddress is not an AWS address, and for userIdentity.principalId AIDA3W7DIFLYOLTK63SFS or AIDAJYRRH5Y3A7AAJM2HW with non-AWS source addresses. Look for quiam- role session names. Enable S3 data events in CloudTrail or S3 server access logs, because management events do not record the object reads that make up the exfiltration. Rotate every secret, parameter and Lambda environment variable the role could read, and revoke active sessions for the role. Remove unused Qubole roles or restrict their trust policies, and add a source IP condition that limits assumption to Qubole's documented network ranges; Wiz states a source IP condition alone would have blocked every role assumption it observed. Use a distinct External ID per role where supported.

Two developments would change the assessment. First, any disclosure of how the Qubole account credentials were obtained, since that determines whether the same access path exists for other vendor integrations. Second, the bootable .iso image Wiz flagged as a hint at additional operations; if the actor deployed persistent tooling rather than only copying data, this becomes an access problem, not a data theft problem.
