Aikido Security researcher Joe Leon found that GitLab's "Email work item to this project" feature mints incoming addresses embedding a long-lived token. The address format looks like incoming+project-id-glimt-...-issue@incoming.gitlab.com, and the glimt- value is an authentication token that does not expire by default. Research showed the same token recurs across email addresses generated for multiple projects of one user, including private repositories, making it an account-scoped credential rather than a project-scoped one. Aikido also found real private project addresses exposed in READMEs, contributing guides, and support pages used to collect bug reports.

The abuse chain is direct. An attacker holding a victim's incoming address changes the -issue suffix to -merge-request and emails a Git patch as an attachment. A source branch named in the subject makes GitLab apply the patch to an existing branch or create a new one under the victim's identity. If the victim's account can push to protected branches, attacker-controlled code lands there, and CI/CD pipelines execute with the victim's permissions. Exposure of CI/CD variables, source code theft, and access to confidential issues follow from the same foothold. GitLab's IP allowlist controls do not stop this because incoming email is explicitly excluded from them.

The practical exposure surface is wide: any developer who pasted a project email into public documentation handed out an unexpiring credential. Watch for a GitLab fix or token rotation mechanism, guidance to regenerate compromised glimt- tokens, and scanning efforts by security teams to find these addresses in public repos and sites. Until token rotation exists, treat any published incoming address as a compromised account credential.
