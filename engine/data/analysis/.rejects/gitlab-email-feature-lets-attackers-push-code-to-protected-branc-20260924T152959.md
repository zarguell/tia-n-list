GitLab's feature for emailing work items into a project can be abused as an account-level code delivery mechanism, according to research by Joe Leon of Aikido Security. The addresses GitLab generates for that purpose embed a long-lived incoming email token, visible in the local part of addresses like incoming+project-id-glimt-...-issue@incoming.gitlab.com. The token does not expire by default, and the same token appears in addresses generated for multiple projects of the same user, including private repositories, which makes it an account-scoped credential rather than a project-scoped one.

An attacker who obtains a victim's incoming email address can change the suffix from -issue to -merge-request and submit a Git patch as an email attachment. By naming a source branch in the subject, the attacker gets GitLab to apply the patch to an existing branch or create a new branch under the victim's identity. Where the victim's account is authorized to push to protected branches, the attacker's code can land on them, and the resulting merge requests execute CI/CD pipelines with the victim's permissions. IP restriction settings do not block this path because incoming email is explicitly excluded from those controls.

The issue is quiet but serious: an incoming email address looks harmless, yet it becomes a code injection primitive against repositories and pipelines once it leaks into issues, documentation, or logs. Watch for GitLab guidance on expiring or rotating incoming email tokens, and audit where project email addresses have been exposed.
