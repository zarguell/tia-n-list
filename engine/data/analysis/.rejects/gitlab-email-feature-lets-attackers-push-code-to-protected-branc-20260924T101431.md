GitLab's "Email work item to this project" feature generates a long-lived incoming email token embedded in addresses like incoming+project-id-glimt--issue@incoming.gitlab.com. Security researcher Joe Leon found the same token works across multiple projects including private repositories, making it an account-scoped credential rather than project-scoped. An attacker who captures the address can change the suffix from -issue to -merge-request, submit a patch attachment, specify a source branch, and cause GitLab to apply the patch under the victim's identity, potentially pushing to protected branches and triggering CI/CD pipelines.

The token does not expire by default and bypasses GitLab IP restrictions because incoming email is explicitly excluded from those controls. Organizations should audit project-level incoming email settings, rotate or disable tokens where not needed, and restrict protected branch push permissions. Watch for GitLab patches that enforce token expiration or scope restrictions.
