GitLab's "Email work item to this project" feature mints incoming email addresses of the form incoming+<project-id>-glimt-<suffix>@incoming.gitlab.com, and security researcher Joe Leon of Aikido Security found the glimt- segment is an authentication token that does not expire by default. Although GitLab presents the address as a project-specific issue-creation method, the same token appears in addresses generated for multiple projects belonging to the same user, including private repositories. It is effectively an account-scoped credential with the appearance of a project-scoped one.

Abuse is straightforward for anyone who obtains a victim's incoming address. Changing the -issue suffix to -merge-request and attaching a Git patch makes GitLab apply the patch under the victim's identity, either to an existing branch or to a new one, with the source branch named in the email subject. If the target account is authorized to push to protected branches, attacker-controlled code lands there and CI/CD pipelines execute. The technique also bypasses GitLab's IP restrictions because incoming email traffic is explicitly excluded from those controls.

Treat these addresses as live credentials rather than identifiers. They leak easily through issue notifications, replies-to-all, and public trackers. Until GitLab issues a fix or guidance, disable or restrict the email work-item feature on sensitive projects, audit for unexpected merge requests or branches created through inbound email, and rotate exposed incoming addresses. No CVE has been assigned in the reporting so far, so tracking depends on GitLab's own advisories.
