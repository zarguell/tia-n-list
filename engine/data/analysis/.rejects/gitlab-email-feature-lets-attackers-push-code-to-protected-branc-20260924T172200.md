Joe Leon of Aikido Security found that GitLab's "Email work item to this project" feature issues addresses that embed a long-lived authentication token. The address format looks like incoming+project-id-glimt-<token>-issue@incoming.gitlab.com, and the glimt token does not expire by default. Research showed the same token appears in addresses for multiple projects belonging to the same user, including private repositories, making it an account-scoped credential rather than the project-scoped one the UI suggests.

An attacker who obtains a victim's incoming-email address can change the suffix from -issue to -merge-request and email a Git patch as an attachment. By naming a source branch in the subject, the attacker gets GitLab to apply the patch to an existing branch or create a new branch under the victim's identity, triggering merge requests and CI/CD pipelines with the victim's permissions. If the account can push to a protected branch, attacker-controlled code can reach main and execute CI jobs. The technique also bypasses GitLab's IP restrictions, since incoming email is explicitly excluded from those controls.

The exposure is practical, not theoretical: these addresses exist to be shared in issue trackers and documentation, and anyone who harvests one from a public project gets a durable credential to its owner's broader GitLab footprint.

Worth watching: whether GitLab scopes the token per project or adds expiry, whether the -merge-request path gets disabled or rate-limited, and whether organizations rotate exposed incoming addresses found in public repos and issue threads.
