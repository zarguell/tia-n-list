GitLab's "Email work item to this project" feature embeds a long-lived credential in the per-project email addresses it generates. Security researcher Joe Leon of Aikido Security found that addresses in the format incoming+project-id-glimt-<token>-issue@incoming.gitlab.com carry a glimt token that does not expire by default. The same token appears in addresses generated for multiple projects, including private repositories, so the secret works as an account-scoped credential rather than a project-scoped one.

An attacker who obtains a victim's incoming address can change the -issue suffix to -merge-request and submit a Git patch as an email attachment. The subject line sets the source branch, so GitLab applies the patch to an existing branch or creates a new one under the victim's identity. If that account is authorized to push to protected branches, attacker-controlled code lands directly on them, and the resulting merge requests execute CI/CD pipelines with the owner's permissions.

The abuse path also bypasses GitLab's IP restrictions, since incoming email is explicitly excluded from those controls. Any address shared in tickets, documentation, or forwarded mail is therefore a standing credential for code delivery, and default token behavior gives it no expiry. Teams using email-based work item creation should treat issued addresses as secrets, audit where they have been exposed, and limit which accounts hold push rights to protected branches while this is unaddressed.
