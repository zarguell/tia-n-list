GitLab's "Email work item to this project" feature embeds a long-lived credential in the incoming addresses it generates for creating issues, in a format like incoming+project-id-glimt-<token>-issue@incoming.gitlab.com. Joe Leon of Aikido Security found that the glimt token does not expire by default and is account-scoped rather than project-scoped: the same token appears in addresses generated for multiple projects, including private repositories, even though GitLab presents each address as a project-specific method.

The token is enough to move code, not just create tickets. An attacker holding a victim's address can change the suffix from -issue to -merge-request, attach a Git patch, and name a source branch in the email subject. GitLab applies the patch to an existing branch or creates a new branch under the victim's identity. Where the victim's account is authorized to push to protected branches, the attacker can land commits on those branches and execute CI/CD pipelines with the victim's permissions. GBHackers' write-up adds that the technique bypasses GitLab's IP restrictions because incoming email is explicitly excluded from those controls.

Everything hinges on the secrecy of one non-expiring string that travels through email. Watch for GitLab guidance on token rotation, scoping, or disabling the email-to-work-item feature, and treat any exposure of these addresses in forwarded mail, ticketing exports, or integration logs as credential compromise rather than a cosmetic leak.
