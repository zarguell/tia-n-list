Aikido Security researcher Joe Leon found that GitLab's "Email work item to this project" feature embeds a credential that behaves like a long-lived account token rather than a project-scoped address. The generated addresses follow the pattern incoming+project-id-glimt-...-issue@incoming.gitlab.com, and the glimt- value does not expire by default. The same token appears in addresses generated for multiple projects, including private repositories, so one leaked address effectively exposes an account-wide credential.

Abuse is straightforward once the address leaks. An attacker changes the -issue suffix to -merge-request and emails a Git patch as an attachment; a source branch named in the subject tells GitLab to apply the patch to an existing branch or create a new one under the victim's identity. If the compromised account can push to protected branches, the attacker inherits that ability and can also trigger CI/CD pipelines with the token owner's permissions. GBHackers adds that the path bypasses GitLab IP restrictions, because incoming email is explicitly excluded from those controls.

The exposure model is realistic: these addresses sit in project settings, onboarding docs, and notification chains, and forwarding one leaks a non-expiring credential. Watch for a GitLab advisory changing token scoping or expiry, and until then treat any incoming-email address as a secret worth monitoring. Audit which accounts can push to protected branches, since that is the permission that converts email leakage into code execution on main.
