GitLab's "Email work item to this project" option generates a private incoming address of the form incoming+project-id-glimt-...-issue@incoming.gitlab.com so users can create issues by email. Joe Leon of Aikido Security found that the glimt- value in that address is an authentication token that does not expire by default, and that the same token appears in addresses generated for multiple projects of one user, including private repositories. The credential is account-scoped, not project-scoped as the UI implies.

An attacker who obtains a victim's incoming address can change the suffix from -issue to -merge-request and mail in a Git patch as an attachment. The source branch named in the email subject tells GitLab to apply the patch to an existing branch or create a new one under the victim's identity. If that account may push to a protected branch, the attacker inherits that ability and can trigger CI/CD pipelines with attacker-controlled code. Aikido also notes incoming email is explicitly excluded from GitLab's IP restrictions, so allowlisting does not stop this path.

The exposure is the address itself: any leak of a project's incoming address, from a forwarded ticket to a public issue, becomes an account-level code delivery channel. Projects should treat these addresses as secrets, rotate them where possible, and audit protected-branch push permissions for accounts whose addresses may have leaked. Watch for GitLab scoping the token per project or adding expiry, and for a CVE assignment once the issue is tracked.
