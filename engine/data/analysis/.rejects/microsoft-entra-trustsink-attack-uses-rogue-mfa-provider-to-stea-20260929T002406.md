TrustSink is a post-compromise credential phishing technique against Microsoft Entra, documented by Varonis, that abuses External Authentication Methods (EAMs). An attacker who already holds Global Administrator or Authentication Policy Administrator privileges registers a rogue EAM, which takes an application registration, a service principal, and a publicly reachable HTTPS endpoint. Entra then treats the attacker-controlled service as the MFA provider for users assigned to it.

The flow abuses real trust in the sign-in chain. The user first types their password on Microsoft's genuine sign-in page. When MFA starts, Entra redirects the browser to the rogue provider, which displays a convincing copy of the Microsoft password page instead of a second factor. If the user re-enters the password, the attacker's server records it in plaintext, then returns a signed token asserting the authentication check passed. Entra validates the token and completes the sign-in. In Varonis's test tenant, built with a small OpenID Connect server, users reached their applications without errors while the researchers' server collected passwords, timestamps, and source IP addresses. The root cause: a valid signed token proves token validity, not that the provider actually showed a genuine MFA challenge.

The precondition is high tenant privileges, so this is a what-next technique after an admin takeover, not an initial access vector. It matters because it turns a legitimate federation feature into a password trap that defeats user vigilance, and because resetting a phished password does not remove the trap while the rogue EAM stays registered. Watch for new EAM provider registrations, unfamiliar app registrations and service principals with redirect endpoints, and Entra audit events around authentication method policies; removing the rogue EAM and rotating credentials has to happen together.
