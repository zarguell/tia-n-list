CVE-2026-73570 is an unauthenticated OS command injection (CWE-78) in the SNMP notification component of Zimbra Collaboration Suite. Exploitation requires ZCS below 10.1.20 with the optional zimbra-snmp package installed and SNMP notifications enabled; a crafted SMTP request on port 25, 465, or 587 then executes commands as the zimbra user. PT ESC's IR team documented the TargetZimbra ransomware chain built on it: attackers first drop version.txt or versions.txt into /opt/zimbra/jetty_base/webapps/zimbra/public/ as a marker, plant JSP web shells in the same directory, inject the Gsocket tool, then run a Go encryptor that applies ChaCha20 across /opt/zimbra/ and its subdirectories, renames files to .elock, writes !README_RECOVER.txt notes, and deletes itself. NVD scores the flaw 8.9 and CISA catalogued it as exploited on 2026-08-21.

The disclosure-to-crime timeline is the argument. Zimbra disclosed the SNMP flaw on 26 June 2026 and shipped the permanent fix in 10.1.20 on 20 July 2026; NVD published on 13 August; CISA listed active exploitation on 21 August with a 24 August federal patch deadline; PT ESC reports mass attacks since mid-August and published its full forensic writeup only on 16 September. That is roughly two months in which any ZCS host with a default-adjacent SNMP package sat one SMTP packet away from a webshell, a Gsocket channel, and an encrypted mailstore. The payload targets /opt/zimbra/ itself, so a successful hit means loss of every mailbox the organization owns, and because the actors held interactive access before encrypting, exfiltration for double extortion must be assumed. PT ESC also stresses the same entry point serves miners and APT groups, so an unpatched server with no .elock files is not a clean server. Anyone running ZCS below 10.1.20 with zimbra-snmp still installed is in the exposed population right now.

Patch to 10.1.20 or later, and treat reinstalling the OS with migrated mail data as the gold standard for any server that shows prior indicators. If patching must wait, disable SNMP notifications and remove the zimbra-snmp package. Hunt with the specifics PT ESC published: grep "changed from stopped to" /var/log/maillog, where a shell command preceding that string marks exploitation; run find with -newermt and -newerBt 2026-07-01 under /opt/zimbra/jetty_base/webapps/zimbra/ for out-of-place JSP files; check /var/log/nginx/access.log for 200 responses to non-standard JSPs in the public/ path. On disk, look for version.txt or versions.txt in that public directory, /opt/zimbra/log/defunct for Gsocket, runloop.sh, !README_RECOVER.txt, elockc[a-z] binaries, and *.elock files. Restrict the 13 campaign IPs and the 10 Gsocket addresses plus gsocket.io and *.gs.thc.org at the perimeter.

Two developments would change this assessment. Confirmation of a named group behind TargetZimbra, or a KEV update from Unknown to known ransomware use, would raise scanner and patch pressure and justify treating every internet-exposed ZCS host as an incident candidate. And any evidence of exploitation that drops the SNMP prerequisites, meaning compromise of servers without zimbra-snmp or with notifications disabled, would multiply the exposed population far beyond the current narrow footprint.
