Accomplish principal security researcher Oren Yomtov reported the flaw through Cloudflare's HackerOne program on September 4, 2026 (report 3997565). The root cause sat in dm-thin thin-provisioning pools configured with skip_block_zeroing and 64 KiB blocks. Cloudflare runs each Container in a Firecracker microVM with the root disk presented as /dev/vdc, and when a container's thin volume was deleted its physical blocks returned to a pool shared across customer accounts. A 4 KiB write to an unmapped region forced allocation of a reused 64 KiB block, leaving the other roughly 60 KiB holding the previous tenant's data in readable form.

The researchers recovered residual material widely: foreign data on 18 of 24 placements and 20 of 22 underlying nodes across four continents, with 2,700 distinct foreign directory inodes identified through ext4 directory block checksums. Recovered material included directory listings, SQLite databases, Chromium profiles, .env files, and credential files. The same disk implementation backed Cloudflare Sandboxes and Browser Run, so the exposure was not limited to Containers.

Cloudflare removed skip_block_zeroing fleet-wide, retired running container disks, and cleared pre-mitigation cached image snapshots, finishing rollout September 7 and snapshot cleanup September 19. A review of retained disk-I/O telemetry found no sign of exploitation. Customers needed no configuration changes.

The finding is the sixth published sandbox escape from this team since July 2026, following SharedRoot against Claude Cowork, Beltdown against Claude Code, Beltdown2 against Cursor CLI, a Docker VMM escape, and an OpenAI Codex sandbox escape. Watch for more cross-tenant storage issues in multi-tenant sandbox platforms, since the pattern of reused physical blocks without zeroing likely exists elsewhere.
