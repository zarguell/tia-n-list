Composer, the PHP dependency manager, shipped 2.11.2 on its current branch and 2.2.32 on the long-term support branch to fix three vulnerabilities. The most severe is a command execution flaw rated CVSS 8.8 that a crafted composer.lock file can trigger. The 2.11.2 release notes also credit GHSA-w6hj-6587-3jh5, a fix for malicious zip archives writing outside the package directory through symlinked entries when extraction falls back from unzip to ZipArchive.

composer.lock is committed to repositories and consumed by automated build and deployment pipelines, so a crafted lock file can reach a developer workstation or CI runner through a cloned repository or a malicious dependency update. Command execution at install or update time gives an attacker code execution in the build context, where secrets, tokens, and deployment credentials commonly live. The exposed asset is the pipeline rather than the production application, and the trigger is a file developers are trained to commit and trust. That distinction is why this story matters more than a routine dependency update: every CI job that runs composer install on an untrusted checkout is a potential execution point.

Upgrade developer workstations and CI images to 2.11.2 or 2.2.32, and audit composer.lock files from untrusted sources before running install or update. Run Composer in CI with minimum credentials and prefer pinned, internally mirrored dependencies over resolving from public repositories. Hunt for unexpected package additions in composer.lock, for composer install or update activity against forks and pull requests, and for the GHSA-w6hj-6587-3jh5 extraction path where unzip is unavailable and ZipArchive is used.

Watch for the vendor to publish CVE identifiers for the fixed flaws and for exploit code that targets the lock file parser. A second watch item is public proof of concept for the GHSA-w6hj-6587-3jh5 symlink extraction path.
