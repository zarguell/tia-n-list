Windows researcher Pedro Gabaldon Juliá published a two-part analysis of ZDI-26-708 (ZDI-CAN-29849), a cross-context proxy authentication coercion issue in the Windows Network Connectivity Status Indicator. Microsoft declined to assign a CVE and has not patched it, classifying the behavior as Moderate, Spoofing under its Security Servicing Criteria, so ZDI released it as a 0-day advisory with a CVSS of 5.3. The affected component is ncsi.dll, hosted by the netprofm service and running as NT AUTHORITY\NETWORK SERVICE.

The bug is a context mismatch. An unprivileged user can set a manual proxy or a PAC/WPAD URL, and NCSI's active probe then connects through that attacker-chosen proxy, but the request and its NTLM authentication run in the service's context, which on domain-joined machines represents the computer account. The researcher traced the root cause to NCSI calling WinHttpSetOption with value 0x100, which only disables proxy authentication for local proxies, instead of the 0x04 bit that actually disables NTLM, so a non-local proxy still receives the NTLM exchange. Proxy changes reach NCSI through WinINet Event ID 5600 and a WNF callback, with no impersonation of the configuring user. A reproduction with impacket-ntlmrelayx as WPAD and HTTP proxy captured the authentication from the netprofm process. The same researcher links an ITRESIT Labs post from September 28 describing privilege escalation using NCSI active probes found during a client engagement.

The practical risk is an authentication-coercion primitive rather than a turnkey exploit: the author is explicit that a useful relay still depends on domain join, the negotiated protocol, and a target without signing or channel binding. Where it lands, the machine-account authentication can feed relay paths such as ADCS attacks or RBCD. Watch whether Microsoft revises the Moderate rating under pressure, and treat unpatched-domain clients as coercion sources: enforcing SMB/LDAP signing and channel binding shrinks the relay surface this enables.
