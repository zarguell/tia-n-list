Ransom-ISAC documented that the DPRK-attributed XCTDH campaign (Cross-Chain TxDataHiding, first documented in October 2025) added a new Ethereum-based recovery channel called HashHiding in malware samples from September 2026. The campaign already used TRON transactions, with Aptos as a fallback, as indexes pointing to BNB Smart Chain transactions whose input field carries encrypted JavaScript that infected hosts decrypt and run. In that original chain BSC stores the payloads while TRON and Aptos act as pointers. HashHiding serves a different purpose: it stores no code, only the current command-and-control address.

The mechanics are simple and resilient. A JavaScript module named _Z scans Ethereum blocks for ordinary transfers from an operator-controlled wallet and reads the first six bytes of the recipient address as four bytes of IPv4 address plus two bytes of port number. That decoded endpoint lets the malware fetch fresh bootstrap code. Because the address rides inside routine ETH transfers, there are no domains or smart contracts to sinkhole and no transaction to flag as malicious; seizing one C2 server accomplishes little because the next one is published on-chain. OpenSourceMalware independently described the same recipient-address technique as NullReceiver in August 2026, and the x:2104523549759459519 post traces the finding to Ransom-ISAC's own writeup on ransom-isac.org.

Defenders monitoring DPRK-linked intrusion sets should assume blockchain-based C2 recovery will spread to other tooling, since it removes the usual takedown leverage. Worth watching: whether Ransom-ISAC publishes victim or campaign scope for the September samples, detection guidance keyed to Ethereum transactions whose recipient addresses decode to valid IP endpoints, and any evidence HashHiding is adopted beyond this actor's malware.
