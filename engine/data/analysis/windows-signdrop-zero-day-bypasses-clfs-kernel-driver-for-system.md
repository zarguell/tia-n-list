A researcher using the handle MSNightmare published a working local privilege-escalation exploit named SignDrop on GitHub on November 10, 2026, targeting an unpatched flaw in the Windows Common Log File System driver clfs.sys. The bug carries no CVE and no CVSS score, and Microsoft had issued neither an advisory nor a patch as of November 11. SignDrop abuses the CLFS authentication mitigation that reached release builds on or after October 28, 2025: the driver stores a hash-based message authentication code for each log in a .cnpf file beside it, and the exploit coerces a privileged process, in the proof of concept the Defender antimalware engine via ServerMpUpdateEngineSignature, into opening a log that a standard user prepared, so the missing signature file is written as SYSTEM and inherits the original file's DACL. It was tested on Windows 11 26H2, 26H2 Experimental, and Windows Server 2025 Experimental, and a successful run spawns a SYSTEM shell.

The significance is not another clfs.sys memory-corruption bug. It is that Microsoft's own defense becomes the escalation primitive, and that the file-creation request originates inside the security product's trusted process, so kernel-mode self-protection sees a legitimate actor rather than the attacker. The researcher further claims the same path can disable other antivirus and EDR products, and while that specific claim is unverified, it means the very tools a defender leans on for detection can be blinded by the primitive that grants SYSTEM. Because the code is public and needs only an existing standard-user foothold, any commodity loader or ransomware crew already on a box can wrap it, and exposure is confined to hosts where the CLFS authentication mitigation is active, a set that the rollout since late October 2025 has been steadily enlarging across Windows 11 25H2 and Server 2025 fleets, though the researcher's "80% of the world's Windows installations" estimate is unsupported.

There is no patch, so the practical control is to establish whether a host is in the vulnerable state. Under HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\CLFS\Authentication\Mode a value of 0 or 1 places the machine in learning or enforcement mode and makes it vulnerable, while 2 or 3 does not. Disabling the mitigation is not a safe workaround because it reopens the CLFS parsing corruption the mitigation was built to close, and as of November 11 there are no confirmed in-the-wild victims and no CISA KEV entry. Hunt for .cnpf signature files created for user-writable log paths and for Defender engine activity (ServerMpUpdateEngineSignature) touching CLFS containers that a standard user created, since those are the observable artifacts the technique leaves behind.

Watch for a Microsoft out-of-band advisory or a CVE assignment with a clfs.sys fix, which would convert this from an open zero-day into a patch race. Also watch for the proof of concept being folded into post-exploitation frameworks or ransomware loaders, and for the first credible in-the-wild report or CISA KEV listing, any of which would move the assessment from a public PoC toward active abuse.
