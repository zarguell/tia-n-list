Gradle 9.9.1 and 8.14.7, both published on 2026-11-10, fix three vulnerabilities in `org.gradle:gradle-core`; the critical one, GHSA-3cfg-jpcr-gfp3, is a code injection in version catalog accessor generation rated CVSS 4.0 9.3 with no CVE assigned yet. Gradle copies version catalog values into generated Java accessor source without escaping them, so a crafted version, dependency coordinate or plugin id appends executable code that runs when the catalog is loaded during settings evaluation, before any build script and even in builds that never reference the catalog entry. The affected ranges are 7.0 through 8.14.6 and 9.0.0 through 9.9.0; the open source fixes are 9.9.1 and 8.14.7, with 9.8.3 down to 9.2.3 and 7.6.8 only under the paid Gradle Security Subscription. The patched Gradle rejects entries containing `*/` or `\u` at catalog load time, so a build that now fails with "contains '*/', which is not allowed" is declaring a catalog that already carries a payload.

The reason this outranks the other two fixes in the same release is that it breaks the assumption every build engineer relies on: a catalog is data. Dependency verification, checksum pinning and review of `build.gradle` all assume the settings phase only reads configuration, and here the read is the execution, so a poisoned catalog version compromises every project that resolves it while the publisher needs no access to the build machine at all. That turns a shared internal platform catalog, the pattern most large Java shops moved to for exactly this convenience, into a single point of compromise across an entire estate, and IDE synchronization extends the same execution to developers who never invoke a command line build. The subscription-only 7.6.8 fix means shops still on the 7.x line have no free upgrade path, so the long tail of frozen enterprise builds stays exposed even after the advisory is a week old.

Upgrade to 9.9.1 or 8.14.7 on the open source distributions, or to 9.8.3, 9.7.3, 9.6.3, 9.5.3, 9.4.3, 9.3.3, 9.2.3 and 7.6.8 if you hold a Security Subscription, and treat every other 9.x and 8.x build as affected until then. Hunt the local catalogs with `grep -rn -e '\*/' -e '\\u' --include='*.toml' .` across `gradle/libs.versions.toml`, any additional catalog TOML files and catalogs declared inline in settings scripts, and check the generated accessor sources Gradle leaves behind with `grep -rnE '\*/.*[^[:space:]]' ~/.gradle/caches/*/dependencies-accessors/`. Pin published catalog imports to fixed versions rather than `1.+`, `latest.release` or `-SNAPSHOT`, since a moving version silently pulls the payload in without a build change, and enable dependency verification so a substituted artifact under the pinned version fails the build. Audit `org.gradle.daemon.registry.base` in project `gradle.properties` at the same time, because the 8.6 and 7.0 issues fixed in this release are both reachable from a project-supplied file.

Two things would change the assessment: a CVE assignment and any public proof of concept, since the advisory says Gradle has a working exploit and has chosen not to release it, which caps the near-term risk to whoever can reconstruct the trick from the patch diff. The other is the downstream adoption curve. Apache Kafka and Apache Grails had wrapper bump pull requests open within days of the release, and if the major build systems and IDE templates propagate 9.9.1 quickly the practical exposure collapses to unmaintained internal projects, whereas slow pickup leaves a wide window for a malicious catalog on a public repository.
