CVE-2026-129975 is a critical double free in GPGME, the library applications use to talk to GnuPG. read_status() and read_colon_line() in src/engine-gpg.c copy the status or colon buffer into a local pointer, grow it with realloc() from an initial 1,024 bytes, and write the new pointer back to the engine context only on success. Early returns leave the context holding freed memory that is freed again at release, and a crafted OpenPGP key with a very long user ID is the reported trigger. GnuPG says all software using GPGME before 2.3.0 is affected and issued 2.3.1 as the public fix; 2.3.0 was never publicly available. Gpg4win 5.1.2 and updated GnuPG Desktop and VS-Desktop builds shipped with the fix.

This is a data-exfiltration primitive in a shared parsing layer, not a bug in one mail client. GnuPG says the double free can pull data out of an application, for example by sending it signed data, and does not rule out remote code execution; Debian DSA-6646-1 lists information disclosure, denial of service and possible arbitrary code execution. No victims or in-the-wild use appear in either report. The advisory names Gpg4win, GnuPG Desktop, VS-Desktop, most mail clients, many XMPP clients, Samba and Flatpak, and exposure includes statically linked copies that package-level inventories miss. The record carries 2 sources, a score of 5.1, no Reddit signal, KEV false and EPSS 0.0, but those signals understate a library-level bug where parsing an attacker-supplied key can touch the process holding secrets. GnuPG's task was opened on 13 November, and disclosure was moved from 25 November to 20 November because of a separate Ruby2Shell bug at GitLab, shortening the public window for downstream builders.

Patch the shared library to GPGME 2.3.1, take the DLL from Gpg4win 5.1.2, and rebuild statically linked programs against 2.3.1; Debian trixie users need gpgme1.0 1.24.2-3+deb13u1 from DSA-6646-1. GnuPG supplies an attached patch for older versions that cannot move and says GPGMEPP and GPGMEQT do not need updating. Where key retrieval is automatic, gate keys arriving from keyservers or untrusted attachments until the parser is fixed. No IoCs, log paths or exploit strings are published in the record, so the hunt is inventory and crash telemetry: find every host carrying a GPGME version below 2.3.0, include DLLs and embedded static builds, and look for allocator or crash reports in processes that call read_status() or read_colon_line() on untrusted keys.

Watch for downstream advisories from mail, XMPP, Samba and Flatpak distributors that name bundled GPGME versions, and for a public trigger key or any report of exploitation; the current record describes neither. A confirmed in-the-wild key, or evidence that the stale-pointer path is reachable with less than a crafted long user ID and an early return, would turn this from a broad patching problem into active incident response. The abandoned 25 November coordinated date is the checkpoint for downstream projects still shipping a pre-2.3.0 build.
