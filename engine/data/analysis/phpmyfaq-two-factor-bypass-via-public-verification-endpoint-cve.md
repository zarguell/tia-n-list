CVE-2026-56737 is an authentication bypass in phpMyFAQ, tracked as GHSA-8gpw-xvpf-hvx5 and rated High at CVSS 8.1 by GitHub, that affects the composer package phpmyfaq/phpmyfaq from 3.2.0 through versions below 4.1.6, with the fix released in 4.1.6. The public two-factor verification endpoint POST /check logs a user in on a valid 6-digit TOTP token and an attacker-chosen user-id alone, with no server-side state binding the step to a prior successful password authentication. The admin login flow does bind it correctly through a 2fa_pending_user_id session value set only after password validation, which is why the reporter treats the frontend omission as a regression. The net effect is that for every 2FA-enabled account, including administrators, the password factor disappears and the only remaining barrier is a 6-digit code, classified as CWE-287 and CWE-306.

Two aggravating details raise the practical risk. The /check endpoint has no failed-attempt lockout, and phpMyFAQ's per-account login throttle is disabled by default, so the TOTP space is brute-forceable across time windows; a proof-of-concept in the advisory iterates the token space against user-id 1, the default first and admin account. The bypass is not universal: validateToken() returns false for accounts without a stored secret, so only 2FA-enabled accounts are exposed, but 2FA is the hardening step administrators are told to enable. Reported by waseem-cve, the advisory was published to GitHub on July 13 and surfaced in the NVD in late September, which is what put it back in circulation.

Deployments should move to 4.1.6, which carries the fix commits, and in the meantime restrict network access to phpMyFAQ frontends and monitor for POST /check bursts against a single user-id, the signature of token brute-forcing. Audit which accounts have 2FA enabled, since those are exactly the accounts this flaw reduces to one guessable factor.

What to watch: any vendor statement on how many installs run vulnerable versions, and whether exploitation shows up in the wild, since a brute-forced admin session on a FAQ platform is quiet by design. The advisory was known internally since July, so the window between the July fix and the NVD publication is where mass-scanning interest typically spikes.
