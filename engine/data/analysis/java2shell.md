Java4Shell, tracked as CVE-2026-114938, was disclosed on 17 November 2026 as a heap out-of-bounds write in the AVX-512 VBMI accelerated Base64 decoder in OpenJDK. Calif scored the flaw 9.2 under CVSS 4.0, Oracle 8.1 under CVSS 3.1. A short malformed padded tail makes the assembly path write 62 bytes past the output buffer. The affected code landed in JDK 18 and was backported to 17.0.6, so unpatched 17.0.6 and later, plus the 21, 25 and 27 lines before the November fixes, are in scope on x86-64 CPUs with AVX-512 VBMI. Standard Java 8 and 11, ARM64 hosts and older Xeons without VBMI are not affected by this path.

Calif demonstrated pre-authentication remote code execution on default installs of Keycloak, Jira, Confluence, JFrog Artifactory, Jenkins and PingFederate, and authenticated code execution on Kafka Broker, Solr, Elasticsearch, Gerrit and Spinnaker. Oracle and OpenJDK shipped fixes on 17 November, with rebuilt versions 17.0.21.1, 21.0.13.1, 25.0.5.1 and 27.0.1.1. Where patching has to wait, disabling the intrinsic with -XX:-UseBASE64Intrinsics or limiting AVX with -XX:UseAVX=2 closes the vulnerable path. CISA urged immediate patching; Cisco Talos said it had not observed in-the-wild use, and GreyNoise began monitoring scanning and exploitation attempts.

Exposure depends on the runtime build and the host CPU as much as on application code, so inventory JVMs in container images and on x86-64 hosts before assuming a dependency scan covered them. The same image can be vulnerable on one host and inert on another. Cisco advisories in the coverage map Java4Shell into products also tracked under CVE-2026-76411, CVE-2026-76414 and CVE-2026-76415, while Oracle's November update carried 655 security updates covering 640 CVEs. Prioritize internet-facing identity, CI/CD and collaboration systems, and treat any heap corruption or unexpected JVM crash on an affected CPU as a lead.
