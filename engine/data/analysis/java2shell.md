CVE-2026-114938, named Java4Shell by Calif, is a heap out-of-bounds write in the AVX-512 accelerated Base64 decoder in OpenJDK's HotSpot JVM. Calif disclosed it on 17 November 2026, the same day Oracle and OpenJDK shipped fixes. A malformed padded Base64 tail makes the decoder write 62 bytes past the end of its output buffer before Java rejects the input. One reconstruction uses 128 'A' characters plus '=' on JDK 17, or 65 bytes on branches with a 64 byte break-even. The vulnerable path runs on x86-64 CPUs with AVX-512 VBMI, including Intel Xeon Ice Lake through Granite Rapids and AMD EPYC Zen 4 onward. ARM64 and older x86 processors are not affected. The code landed in JDK 18 and was backported to 17.0.6, so 17.0.0 through 17.0.5, 11 and 8 are clean apart from the noted 8u511b33-perf build.

Impact goes beyond a crash. Calif describes reading past a corrupted array length and calls that capability JavaBleed, with heap data that can include private keys, tokens and personal data. Researchers demonstrated pre-authentication code execution against default installs of Keycloak, Jira, Confluence, JFrog Artifactory, Jenkins and PingFederate, and authenticated code execution against Kafka Broker, Solr, Elasticsearch, Gerrit and Spinnaker. The SOC Prime write-up adds Spring Boot and Apache Struts sample applications. Calif rates the flaw 9.2 under CVSS 4.0 while Oracle assigns 8.1 under CVSS 3.1. Talos reported no observed in-the-wild use, Tenable saw none as of 17 November, and GreyNoise is monitoring scanning and exploitation attempts. A trigger PoC is public, while application-specific exploits are being withheld.

Fixed builds named in the material are 17.0.21.1, 21.0.13.1, 25.0.5.1 and 27.0.1.1. The upstream fix is a four line guard in stubGenerator_x86_64.cpp that sends short padded tails to the Java fallback path. Where patching has to wait, the documented stopgaps are -XX:-UseBASE64Intrinsics or -XX:UseAVX=2. Inventory has to cover JVMs inside container images as well as hosts, because dependency scanning alone will not show which runtime is running. Internet-facing identity, CI/CD and collaboration systems that decode attacker-supplied Base64 are the first systems to check, and downstream vendors are shipping patched builds on separate schedules.
