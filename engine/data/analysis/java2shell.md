Java4Shell is CVE-2026-114938, a heap out-of-bounds write in the AVX-512 accelerated Base64 decoder in OpenJDK's HotSpot JVM. Calif disclosed it on November 17, 2026, the same day Oracle and OpenJDK shipped fixes. A malformed padded Base64 tail makes the decoder write 62 bytes past the end of its output buffer. One writeup reproduces the trigger as 128 'A' characters plus '=' on JDK 17, or a 65 byte input on branches with a 64 byte break-even. The bug affects OpenJDK 17.0.6 and later on x86-64 CPUs with AVX-512 VBMI, including Intel Xeon from Ice Lake through Granite Rapids and AMD EPYC from Zen 4 onward. ARM64 and older x86 processors are not on the affected list.

The impact is not just a crash. Researchers describe reading past a corrupted array length and call the disclosure capability JavaBleed, with heap data that can include private keys, tokens and personal data. Calif reported pre-authentication code execution against default installs of Keycloak, Jira, Confluence, JFrog Artifactory, Jenkins and PingFederate, and authenticated code execution against Kafka Broker, Solr, Elasticsearch, Gerrit and Spinnaker. Exploitation status remains mixed: Talos said it had not observed in-the-wild use, Tenable reported none as of November 17, and GreyNoise is monitoring scanning and exploitation attempts. A trigger PoC is public, while application-specific exploits are being withheld by the discoverers.

Patched builds named in the event material are 17.0.21.1, 21.0.13.1, 25.0.5.1 and 27.0.1.1. Where patching has to wait, the documented stopgaps are -XX:-UseBASE64Intrinsics or -XX:UseAVX=2. Inventory has to cover JVMs inside container images as well as hosts, because dependency scanning alone will not show which runtime is running. Internet-facing identity, CI/CD and collaboration systems that decode attacker-supplied Base64 are the first systems to check, especially given CISA's call to patch immediately.
