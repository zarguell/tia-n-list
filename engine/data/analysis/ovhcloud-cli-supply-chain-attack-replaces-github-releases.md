The OVHcloud CLI supply chain attack is a release-asset replacement, not a build-system breach. Between 12:47 and 13:12 UTC on 19 October 2026, an attacker using the compromised contributor account `HassenBF` deleted and re-uploaded binaries for versions v0.11.0 through v0.15.0 via GitHub's Releases API. The malicious build was compiled locally from commit `5ead8ef` (a dirty checkout with uncommitted changes) rather than through GoReleaser, as shown by `vcs.modified=true` and the pseudo-version `v0.15.1-0.20261013083505-5ead8ef9b43d+dirty` recorded in the binary's `go version -m` output. The attacker replaced six assets per version (Linux x86_64/arm64, macOS x86_64/arm64, Windows x86_64, and the matching `checksums.txt`), leaving only the less-used i386, Windows arm64, and WASM builds untouched. A downstream user whose CI pinned the SHA-256 `5c2beb56e6d83a4b426565a1557791ef759316abcc4effb38dd627c90aeb80e0` for v0.15.0 Linux arm64 caught the swap at 13:50 UTC and filed public GitHub issue #300, which remains the primary forensic source.

This matters because the exposure window was 94 minutes, the malicious binary reads secrets from disk, and anyone who installed through `install.sh`, Homebrew, or a direct tarball download during that window on macOS, Linux x86_64/arm64, or Windows x86_64 must treat the machine as fully compromised. The attacker did not touch the source repository or push tags, so `go install` and Docker users who pulled `ovhcom/ovhcloud-cli` (built by OVHcloud's internal pipeline) were unaffected. What makes this story harder to ignore than the average GitHub release swap is the account history: `HassenBF` had been force-pushing repositories since March 2026 with a hidden `preinstall.js` loader that uses a Solana memo dead drop (`BjVeAjPrSKFiingBn4vZvghsGj9KCE8AJVtbc9S8o8SC`) for stage-two delivery, linking the October replacement to the GlassWorm actor group through shared wallet indicators and the same amend-and-force-push technique.

Defenders should treat installations from v0.11.0 to v0.15.0 between 12:47 and 14:21 UTC on 19 October as malicious. Check any retained binary with `go version -m` for `vcs.*` lines or `+dirty`; clean builds report only the tag version (`v0.15.0`). Verify archive hashes against the originals listed in issue #300 (`3833daffcaaaab27e4e0e0833240ffcb1df8df648f4ec0bc4a75c176e28933cb` for the malicious Linux arm64 build) and rotate all secrets readable from affected hosts, including `~/.ovh.conf`, cloud provider credentials, SSH keys, and `.env` files. Update to v0.16.0 or later (immutable release with attestation), pin SHA-256 in CI, and verify with `gh attestation verify`. Hunt for the throttle file `~/init.json` on macOS and outbound connections to Solana RPC endpoints from build hosts.

Watch for OVHcloud's promised post-mortem covering the initial access to `HassenBF`, whether the attacker obtained the long-lived `TAP_GITHUB_TOKEN` used by `.github/workflows/release.yml`, and download counts for the replaced assets during the 94-minute exposure window. Also monitor for additional GlassWorm campaigns using mutable GitHub releases and Solana memo dead drops, since the same loader pattern and wallet indicator have appeared across multiple repository compromises.
