On October 19, 2026 between 12:47 and 13:12 UTC, an attacker replaced release binaries of five OVHcloud CLI versions, v0.11.0 through v0.15.0, through a compromised GitHub contributor account. The malicious binary was a secret-stealing build compiled from a dirty local checkout rather than the project's GoReleaser pipeline, with build metadata showing vcs.modified=true and pseudo-version v0.15.1-0.20261013083505-5ead8ef9b43d+dirty. The attacker hijacked a developer's GitHub account to reach the OVHcloud CLI repository and modify the tagged releases.

A downstream CI job that pinned a SHA-256 for the Linux arm64 tarball of v0.15.0 failed, exposing the replacement; the reporter captured the malicious binary's metadata before OVHcloud deleted the replaced assets at 14:21 UTC. French cybersecurity outlets reported that OVHcloud confirmed the compromise lasted roughly 94 minutes, making this a targeted supply chain incident with confirmed malicious binary replacement rather than a credential leak. OVHcloud CEO Octave Klaba disclosed the compromise of the CLI repository on GitHub, urging users who downloaded the latest version on October 19 to update or remove the tool. The CLI is an alternative for administrators and developers to manage cloud and hosting services from a terminal, including via automation, so anything scripted against it was running attacker code.

The practical advice is narrow and cheap. Anyone who pulled a release on October 19 should treat every credential reachable from that machine as exposed, including cloud API tokens, SSH keys and CI secrets, and should rotate them rather than wait for a confirmation of exfiltration. Pinning release checksums in CI, which is what surfaced this one, is the control that caught it, and teams should verify their own pin lists against the deleted asset set. The wider question is whether other Go or container toolchains in the same supply chain are exposed, since the same maintainer-account takeover pattern has produced several incidents this year.
