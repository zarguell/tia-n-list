UpGuard's September 25, 2026 study put a number on a pattern researchers have been documenting since March 2025: 16,326 Supabase databases out of roughly 300,000 domains showing Supabase fingerprints serve readable tables to anyone who asks. There is no bug to exploit and no CVE for the class; the client ships a public anon or publishable key by design, and the tables behind it either lack row-level security policies or carry policies that restrict nothing, so a plain GET against the /rest/v1/ endpoint returns full rows. Over half the exposed databases held PII, a smaller subset passwords and authentication tokens, and a very small set plausible credit card data. CVE-2025-48757 named the Lovable-flavored variant of this misconfiguration back in May 2025, and UpGuard's finding is the same failure mode grown to platform scale, now mixed across standalone businesses rather than one builder's output.

The exposure is a breach without an intrusion, and the victim set is defined by one adoption curve: AI-assisted development accounts for more than 60 percent of newly created Supabase databases, yet Supabase's own January 2026 security retro confirms RLS-by-default applies only to tables created in the dashboard, not to tables created programmatically through the API, which is exactly how coding agents like Claude Code build. The platform's growth engine therefore routes through the one path that still ships tables open by default, and the humans involved, in UpGuard's words, do not understand their database's configuration. The readable payloads convert directly into follow-on compromise: 884 plaintext passwords at a Canadian immigration service, over 100,000 customer records with license plates and visit history at a US valet company, 25,000 consulate records with emergency housing locations, and 1.5 million API tokens at Moltbook in February 2026. Credentials and tokens harvested this way feed account takeover at entirely unrelated services, which is why this story outranks the day's ordinary breach news.

Nothing gets patched here; the fix is configuration. Enable RLS on every table in the exposed schema or disable the Data API outright, audit policies for correctness rather than mere existence, and rotate legacy JWT-based anon and service_role keys to revocable publishable and secret keys before Supabase removes legacy keys in late 2026. Run Supabase Security Advisors, act on the email alerts for tables without RLS, and review the platform's advisors documentation and API security guide that BleepingComputer's report points to. The hunt is cheap: pull the JavaScript bundles of sites you own or assess and grep for supabase.co hostnames and sb_publishable or anon key strings, then replay a select=* query against rest/v1/ tables with that public key and treat any returned row as a finding. PostgREST error hints that name accessible tables are the same tell UpGuard and Wiz used, and web logs showing unauthenticated GETs to /rest/v1/ with large row counts are evidence someone else is harvesting.

Two developments would change this assessment. First, credential-stuffing telemetry tying the harvested password and token sets to account takeover waves at major providers would move the story from hygiene problem to active incident. Second, Supabase extending RLS-by-default to API-created tables or accelerating legacy key revocation would shrink the exposed population faster than manual cleanup, while any follow-up research quantifying active harvesting of these 16,326 databases would confirm the second half of the kill chain is already running.
