A Kaspersky GERT investigation found a BlackNevas ransomware engagement that destroyed an organization's virtualization estate over ten days without exploiting any virtualization-layer vulnerability: no guest-to-host escape and no hypervisor memory corruption. The attacker used legitimate VMware management interfaces to hit four ESXi hosts, every virtual machine on them, both vCenter Server Appliances, and all connected backup infrastructure, with ransom notes identifying BlackNevas, first observed in November 2024. The ESXi encryptor was Babuk-derived, reflecting the September 2021 leak of Babuk's ESXi source code that at least ten subsequent families have reused.

The exposure is not a missing patch but a management-plane trust boundary: a monitoring platform (PRTG Network Monitor) with broad host access and a root password reused across several nodes gave the attacker SSH access to every affected ESXi host, and backup infrastructure reached through the same plane was destroyed first. Because guest EDR cannot observe hypervisor-side VMDK modifications, a fully patched estate still falls when privileged credentials are shared or stored in plaintext, which is why this incident is the archetype rather than an outlier. The case also shows execInstalledOnly working as designed until root access disabled it, a 2 KB partial overwrite, and roughly a three-hour self-test window before detonation.

Defenders should isolate vCenter and ESXi management interfaces from the general server network, restrict SSH to dedicated jump hosts, rotate and unique root credentials per host, and remove reusable credentials from monitoring platforms such as PRTG. Hunt for the documented indicators: AnyDesk and GMER execution on Windows systems in the virtualized domain controller segment, UserAssist artifacts, an uploaded `esx` binary, SSH sessions as root from 192.168.*.* addresses, disabling of `/User/execInstalledOnly`, log deletion, and VMDK or datastore modifications outside maintenance windows. Treat backup infrastructure as a separate security boundary and verify it cannot be reached from the virtualization management plane.

Watch for whether BlackNevas or other Babuk-derived ESXi lockers appear in additional incidents reusing this same monitoring-to-hypervisor path, and whether Broadcom or VMware harden execInstalledOnly and SSH logging in future ESXi releases. A shift toward exploiting actual vCenter or ESXi vulnerabilities for initial access would change the control priority from credential hygiene back to patching.
