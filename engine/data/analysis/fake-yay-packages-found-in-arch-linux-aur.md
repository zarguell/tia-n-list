Malicious AUR packages typosquatting yay and paru were uploaded by user marchos1as and contained legitimate upstream code paired with a malicious install script that executed a remote shell with root privileges. The campaign was detected on October 13 and the first event is October 14, with at least 15 fake copies of popular AUR helpers reported; earlier AUR campaigns include a June attack distributing 400 credential-stealing malware packages with rootkit capabilities and a July adoption-lockdown.

The exposure is the entire Arch Linux AUR user base: any user who installed a package named to mimic yay or paru between the upload and detection risk full root compromise. Unlike the June and July campaigns this is a targeted typosquat of the most trusted helper tools, giving the attacker high-value access with minimal effort. The 400-package June incident proves AUR is under systematic abuse, yet this story stands apart because the malicious payload runs at install time via PKGBUILD, requiring no user interaction beyond the install command.

Defenders should audit any AUR package installed since October 13 for files named close to yay or paru, check `/var/log/pacman.log` for installs from marchos1as sources, and block unknown AUR maintainers at the network proxy. Verify the `PKGBUILD` source URL matches upstream exactly; hunt for remote execution of shell scripts during install using process telemetry. Remove the malicious packages from local caches and rebuild from official upstream repositories only.

Watch for an official Arch security advisory naming additional malicious accounts beyond marchos1as, and for reports that the remote install script pulled a second-stage payload rather than a single installer. If more than the 15 reported fake copies are confirmed or the attacker promotes the packages via a coordinated social engineering push, treat this as an active broad-scale supply chain event rather than a contained typosquat.
