The mechanism is a local privilege escalation chain in OpenBSD 7.9. A shared memory attachment counter, shm_nattch, was defined as a signed 16-bit short with a maximum of 32,767, a definition traceable to the original BSD sources roughly 37 years ago. Repeatedly forking a process with shared memory attached could push that counter past its maximum and wrap it to a negative value, producing a use-after-free via a race condition. Combined with a separate out-of-bounds write in the kernel, the chain bypassed OpenBSD's KARL kernel-address randomization plus SMAP and SMEP to reach root. Calif, which found and reported both flaws, published a full writeup and proof-of-concept after OpenBSD shipped patches for both issues in September 2026.

The impact is local only, not remote: an attacker needs an existing unprivileged account or code execution on the host. That still matters because a single low-privilege foothold on any OpenBSD 7.9 system, including firewalls and routers where OpenBSD is commonly deployed, becomes a root shell. The chain is notable because it defeated KARL and hardware protections without an information disclosure vulnerability, by relying on deterministic kernel allocator placement and predictable early-boot structure addresses. That is the argument for treating this as more than another local LPE: it demonstrates a reusable bypass pattern against OpenBSD's hardening model, not just a one-off bug.

Defenders should apply OpenBSD 7.9 errata 026, which fixes the shm_nattch integer overflow, and errata 018, which fixes the separate out-of-bounds write, or upgrade to a patched release. There is no remote mitigation needed, but hosts with untrusted local users or shared multi-tenant shells are the priority. For hunting, look for fork storms combined with repeated shmat and IPC_RMID activity, IP sockets with IP_MULTICAST_TTL set to a non-default value of 2, and churn in SysV shared memory segments; Calif's writeup details the 127-segment mapping and 259-fork wrapping sequence as the operational signature.

Watch whether OpenBSD adopts the mitigations Calif proposed: safe-unlinking in sys/queue.h before TAILQ_REMOVE writes, randomization of the self-referential PTE map base address, and base or runtime randomization of the kernel allocator. Any of those would break the predictable-pointer technique this exploit depends on, while their absence keeps the bypass class viable for the next integer overflow.
