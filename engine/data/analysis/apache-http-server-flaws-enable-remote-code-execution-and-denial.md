The story is two vendor releases stapled together. The November 11, 2026 release, 2.4.71, carries three CVEs: CVE-2026-119618, rated critical, a concurrency bug in the mod_http2 assign_headers function where improper synchronization on shared resources leads to heap corruption and remote code execution, affecting Apache HTTP Server 2.4.55 through 2.4.70 and standalone mod_h2 2.0.8 through 2.0.42; CVE-2026-106023, rated important, a mod_md NULL pointer dereference during request processing affecting 2.4.30 through 2.4.70; and CVE-2026-109163, rated low, a one-byte mod_vhost_alias stack overwrite affecting only 2.4.69 and 2.4.70. The October 2, 2026 story that the timeline leads with is the earlier 2.4.69 release, which closed 20 CVEs rated 5 moderate and 15 low, none rated important or critical.

The claim that matters is that 2.4.69 is not a safe harbor, and the events do not say so outright. An operator who patched to 2.4.69 on the October advisory, exactly as the Apache project recommended at the time, is still exposed to a critical unauthenticated remote code execution flaw in HTTP/2 for another five weeks, because CVE-2026-119618 was not reported to the security team until October 26 and was fixed on November 11. The mod_http2 flaw is the more dangerous of the two CVEs in this story and it is the one that arrived after the coverage, so anyone triaging off the headline will patch the NULL dereference and miss the heap corruption. Exposure scales with the range: mod_http2 has been compiled in by default for years, so every 2.4.55 through 2.4.70 build with HTTP/2 enabled qualifies, while the mod_md crash needs mod_md loaded and configured. CVE-2026-109163 then adds an awkward detail: the only fix that closes all three is 2.4.71, and the intermediate release 2.4.69 and 2.4.70 are themselves affected by a flaw introduced after the previous mod_vhost_alias fix.

Move to 2.4.71. If that is not immediately possible, disable HTTP/2 rather than the whole server, with a Protocols directive that drops h2 from the advertised list, or by not loading mod_http2, and check mod_md deployments since MDServerStatus was flipped to disabled by default in this same release line. Confirm what is actually running before assuming a version: query the server binary for its build, list loaded modules, and inventory which of mod_http2, mod_md and mod_vhost_alias are enabled with VirtualDocumentRoot in use and LimitRequestFieldSize raised above the default. Hunt for the mod_http2 trigger in the access and error logs: a HEADERS frame followed immediately by a RST_STREAM on the same stream, which needs no authentication and no established session, and pair it with child process exit or signal entries in error_log that cluster in time. Treat repeated child crashes on a host with HTTP/2 enabled as the lead indicator, and correlate any mod_md request-path crash on hosts with ACME automation.

Watch two things. First, exploitation telemetry: the vendor credits Anthropic's OSS Scanner as the finder of CVE-2026-119618, which suggests the bug was surfaced by automated code scanning rather than an in-the-wild actor, and no exploited-in-the-wild status is established anywhere in these events. Any GreyNoise, Shadowserver or vendor telemetry showing scanning for the RST_STREAM pattern, or any move of CVE-2026-119618 into a known-exploited catalog, changes this from a patch-now item to an emergency change. Second, distro lag: distributions that backport rather than ship 2.4.71 wholesale may leave the mod_http2 fix out of an otherwise current package, so the fix-version question should be asked per vendor rather than assumed from the Apache release date.
