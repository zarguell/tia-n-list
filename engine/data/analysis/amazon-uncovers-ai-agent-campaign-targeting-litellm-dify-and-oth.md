Amazon's threat intelligence team ran decoy servers to capture what attackers' own AI agents do when pointed at internet-exposed AI application stacks, and found them hunting LiteLLM, One API and Dify instances specifically for the AI provider keys those applications hold. The agents' records show the stolen keys being turned around to run the very models that powered the next round of key hunting, so a single exposed gateway becomes both the target and the compute budget for the next stage.

The reason this matters is that these applications sit in front of expensive, rate-limited provider accounts and rarely get the network isolation given to databases or internal admin planes. A leaked key is not a single-tenant problem: it bills to the victim, burns quota, and can be used to enumerate further keys through whatever the stolen credential can reach. Because the campaign is agent-driven, the scanning pattern is cheap and continuous rather than a hand-run pentest, which raises the floor on what an exposed instance will attract.

What to watch is whether this behaviour appears in incident telemetry rather than only in vendor decoys, and whether provider keys are being rotated after exposure is discovered. Operators of LiteLLM, One API and Dify should treat their provider credentials as exposed-by-default: restrict the gateway to trusted networks, put keys in a secret store with per-key scoping and spend alerts, and check provider-side usage logs for calls that did not originate from known workloads.
