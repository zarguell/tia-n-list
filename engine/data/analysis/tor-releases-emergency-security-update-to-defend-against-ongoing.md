Tor shipped 0.4.9.17 on 13 November 2026 as a rapid response to a distributed denial-of-service campaign that the project says has affected most relay operators. The release carries several security fixes, and developer David Goulet singled out one as especially important for relay DoS defenses because of how those defenses deal with IPv6. The advisory asks operators to upgrade as soon as possible, states no action item is required after upgrading, and says additional defenses are under evaluation with further releases to follow. It is the third build in seventeen days: 0.4.9.15 on 28 October added three denial-of-service defenses against a thunderstorm of directory requests, 0.4.9.16 on 4 November was an emergency build limited to directory authority fixes for a thundering herd of outdated clients in restart loops, and 0.4.9.17 followed on 13 November.

The load is not pointed at the relays themselves, it is pointed at the directory layer behind them: the project's own words place the strain on the few relays serving as fallback directories and on the directory authorities. Every relay that goes down or is too saturated to hold its position hands its share of directory requests to the survivors, so operator attrition compounds rather than averaging out. That is the argument for treating this as infrastructure risk rather than a relay-uptime annoyance. The practical failure for a volunteer operator is not a crash but a demotion, a relay that stays reachable and loses its HSDir flag, which is exactly the symptom one operator reported on 14 November, and a smaller set of HSDir relays means slower hidden service descriptor lookups for everyone using the network. Because the fix only helps relays that actually upgrade, the population still exposed is every relay pinned to 0.4.9.16 or earlier, and the advisory's IPv6 wording implies the flood was reaching relays over IPv6 as well as IPv4.

Relays should move to 0.4.9.17 now, using the tarballs or the Debian packages that shipped with the release, then confirm the running build at startup in the relay log rather than trusting the package manager's version string. After the upgrade there is nothing else to do, but the hunt is in the consensus rather than the CPU graph: check the relay's consensus page for a lost HSDir flag or a drop in consensus weight, correlate the loss against the relay's own logs for the directory-request and circuit-flood counters, and treat any relay that changed nothing except its version as the control case. There is no CVE id in the project's release text and no client-side patch to apply; the exposure is server-side only.

Two developments would change this assessment. The first is the next release in the series, which the project has said is coming, since a fourth build inside three weeks would mean 0.4.9.17 did not close the IPv6 gap. The second is operator telemetry on whether the flood is changing vector again, because a campaign that has already moved once will keep moving, and a relay fleet that patches and then stops watching its directory flags is exactly the fleet that loses them quietly.
