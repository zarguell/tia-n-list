Cacti 1.2.31 carries an unpatched remote code execution flaw that a fresh, unauthenticated HTTP session can reach in four requests, according to researcher ek0ms savi0r, who published proof-of-concept code tracked as 4HTTP2ROOT and 4HTTP2SHELL. The researcher's description is a path from a clean unauthenticated session to command execution as the Cacti server user, with guest access as the hinge. No CVE identifier has been assigned. Cacti is widely deployed as a network monitoring front end with database reach into the devices it polls, so a guest-to-command path turns a read-mostly appliance into a foothold on the monitoring network.

The practical advice attached to the public PoC is to disable guest access. Cacti installations commonly enable guest visibility for uptime dashboards, which is exactly the configuration the chain is reported to require. Because the tool polls infrastructure using stored credentials, any host compromised this way hands over the credential set it uses for polling and alerting, not just the Cacti host itself.

The important gap is that four short posts and a PoC repository are all that is public so far. No exploitation against third parties has been reported, no vendor fix has been named, and the version scope beyond 1.2.31 is unstated. Expect a CVE assignment and a patched release, and until then treat internet-facing Cacti with guest enabled as exposed. Watch Cacti's own repository for the fix commit rather than the aggregators, and check logs for short request sequences from unauthenticated sessions that end in process creation or file writes under the web root.
