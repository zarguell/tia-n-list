Cacti 1.2.31, published 15 June 2026 and still the newest release, hands an anonymous visitor a guest session and CSRF token from `auth_profile.php`. A POST to `auth_profile.php?action=update_data` stores an arbitrary string in the per-user setting `preview_graphs_per_page`, which is meant to hold a page count and is never validated as an integer. `graph_view.php?action=preview` then reads that stored default and feeds it into the concatenated LIMIT fragment built by `get_allowed_graphs()` in `lib/auth.php`, and the PDO path accepts the appended statement, so the guest rewrites `poller_item.arg1` along with `host_id` and `action`. `graph_realtime.php?action=init` starts the realtime poller, which hands `arg1` to `popen()` in `lib/poller.php`. Four requests, no credentials, no CVE identifier, no patch. Researcher ek0ms savi0r reached root only because the lab ran the web tier as root; in a normal deployment the shell lands as `www-data` or `apache`.

The interesting part is that this is the third pre-authentication SQL injection in `graph_view.php` this year. CVE-2026-39893 (the `rfilter` RLIKE clause) and CVE-2026-39955 (unanchored `FILTER_VALIDATE_REGEXP`) were both fixed in 1.2.31, and both fixes hardened request variables. Neither touched the stored defaults those variables feed, which is the whole bug now: the guest write is a prepared statement, so the database stores the malicious string cleanly, and the read path trusts its own table. That is why this story and not the other thirty today. Every one of the four requests is ordinary guest traffic, with no upload, no authentication event and no payload in a URL, and the payoff is not a shell on a graphing box but the credential store Cacti uses to poll routers, switches, PDUs and hosts, plus the SNMP strings and device logins that make the monitoring server the quiet sideways route into management segments. Exposure is narrower than the headline suggests and deeper than it looks: guest access is documented off by default, so the population at risk is the shops that enabled anonymous dashboard sharing without putting Cacti behind a login.

There is no patch to install. Disable the guest user in Console, Configuration, Users, remove it from authentication settings, then confirm from an unauthenticated browser that `graph_view.php` and `graph_realtime.php` no longer render. Put the interface behind a management network or VPN and stop running the web tier or poller as root, which reduces blast radius only. Hunt first in `settings_user` for `preview_graphs_per_page` values that are not integers, and in `poller_item` for `arg1`, `host_id` or `action` changes nobody scheduled. On the web tier, look for one client hitting `auth_profile.php?action=update_data`, `graph_view.php?action=preview` and `graph_realtime.php?action=init` inside ten minutes; that sequence is the entire attack, and the published PoC pins `ds_step=10&size=90` on the realtime request. Also chase PHP warnings about a non-numeric value coming from `graph_view.php`, new files under the Cacti web root that are then served back over HTTP, and shell children spawned by the web or poller account.

Two developments would change the assessment. The first is the fix itself: a vendor advisory or release that binds the LIMIT clause numerically instead of concatenating it, rather than one that adds a fourth request-side filter. As of the develop branch, `get_allowed_graphs()` still builds `LIMIT $sql_limit` at `lib/auth.php:1686-1687` on the 1.3.0 tree, so no remediation is sitting upstream waiting to be tagged and anyone counting on a quiet point release should not. The second is first contact. An internet-facing Cacti with guest enabled is a four-request target with working public code, so honeypot or scanner telemetry showing that three-endpoint sequence arriving from outside would move this from disclosure to campaign, and it would also settle the affected range, which today is a single confirmed version and a guess.
