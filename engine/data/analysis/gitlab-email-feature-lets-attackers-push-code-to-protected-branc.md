Joe Leon of Aikido Security disclosed on September 23 that GitLab's "Email work item to this project" feature embeds a long-lived, account-scoped credential, the glimt- string, in the project email addresses it generates. The token carries nine permissions including repository update and protected branch update. Swapping the -issue suffix in the address to -merge-request makes GitLab open a merge request from an emailed git .patch attachment, so anyone holding the address can push attacker-controlled code with the token owner's permissions and trigger CI/CD jobs. Incoming email is explicitly excluded from GitLab IP restrictions, so allowlists do not stop this path. Aikido found about a dozen live addresses published in READMEs, contributing guides, and support pages, and notes GitLab had closed a May 2026 HackerOne report on the mechanism as intended behavior.

GitLab's shipped fix is documentation-only: a change merged August 10 into milestone 19.3 removed the claim that the token cannot access other data and added wording that incoming email bypasses IP restrictions. The mechanism itself is unchanged. A feature issue proposing that token actions be accepted only from the owner's verified email address was created August 19, remains unassigned, and targets milestone 19.5 due October 9, with maintainers warning a default-on change could break forwarded-mail and automation workflows. GitLab's concurrent critical patch release 19.4.1, 19.3.3, and 19.2.7, flagged by Canada's Cyber Centre as AV26-962 on September 25, addresses other flaws and does not change this design.

Treat any exposed project email address as a working credential to a repository: code push to protected branches, secret collection from CI/CD variables, and access to confidential issues are all in scope for the token owner's rights. Rotate exposed glimt- tokens now, scrub addresses from public documentation, and watch milestone 19.5 for a real sender-verification control.
