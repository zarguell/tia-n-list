GitLab's "Email work item to this project" button generates addresses like incoming+project-path-glimt-TOKEN-issue@incoming.gitlab.com, and the glimt- string is the actual credential: an incoming email token that never expires, is identical across every project the account can reach, and works in private projects too. Joe Leon of Aikido Security showed that swapping the -issue suffix to -merge-request turns the address into a code delivery path: a message carrying a git .patch attachment with a branch name in the subject line gets applied by GitLab to that branch, creating it if it does not exist, as the token owner. If the patch touches .gitlab-ci.yml and the victim's role allows it, the pipeline executes. GitLab does not verify the sender, and incoming email sits outside IP restrictions; Aikido landed a commit on main of a private project allowlisted to a single foreign IP while the same project blocked their browser and git clone. There is no CVE, because GitLab closed the May 2026 HackerOne report as intended behavior.

The exposure is mispriced by design: the UI frames a leaked address as a spam nuisance, but the token behaves like a fine-grained personal access token scoped to all groups and projects, with nine permissions that include merge request creation, repository update, and protected branch update. Aikido confirmed pushing to protected branches of IP-allowlisted private repositories, source exfiltration, reading CI/CD variables, reaching confidential issues through the /move quick action, and pivoting further with CI_JOB_TOKEN. The ceiling is the victim's role, a Guest address is worthless while a Maintainer address reaches protected branches and secrets, and routing requires the project path and ID, public values for public projects, a brute-forceable ID plus a leaked path for private ones. Scope covers every GitLab.com account and every self-managed instance with incoming email enabled, with no setting to disable the feature and GitLab Dedicated apparently out of scope per Aikido's documentation read. In one afternoon Aikido surfaced a dozen live addresses deliberately published in READMEs, contributing guides, and support pages of open source projects, some of them very popular, which makes this a standing supply-chain vector. The vendor's only shipped response, MR !247431 merged August 10, 2026, changed UI and documentation copy; the mechanism is untouched, and since nothing here has a CVE or scanner signature, exposure management will not catch it through vulnerability feeds.

Remediation is credential hygiene, not patching. Rotate the incoming email token preemptively via the reset link on the personal access tokens page; resetting invalidates every project address on the account. Maintainers who ever published an incoming address for bug reports must reset it and scrub the address from READMEs, contributing guides, and support pages. Scan for glimt- strings the way any secret is scanned; Aikido added coverage to Betterleaks for glimt- prefixed tokens, custom prefixes, and pre-glimt formats, covering more variants than GitLab's own detection. Stop treating IP allowlists as security boundaries here, since GitLab's documentation now states incoming email is not subject to them. For hunting, watch merge requests and branch creations attributed to accounts that do not normally push, flag any incoming-authoring MR whose diff touches .gitlab-ci.yml, and review confidential issue /move actions by unexpected accounts, because GitLab attributes mail-path activity to the token owner and it will not surface as an API call or a git push.

Two developments would move this assessment. If GitLab ships work item #617883, email verification for incoming email token actions, currently in New state at milestone 19.5 due October 9, 2026, the attack collapses to requiring control of the victim's mailbox; a bulk-revocation or user-notification mechanism would matter too, since Aikido reported none existed when warning the dozen exposed accounts. Conversely, the first supply-chain incident traced to a commit arriving through incoming email, or mass harvesting of glimt- tokens from public documentation, would turn a design criticism into an active campaign.
