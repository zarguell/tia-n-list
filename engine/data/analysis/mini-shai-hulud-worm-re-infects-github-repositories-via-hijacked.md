The September re-infection wave required no new exploit, no new infrastructure, and no attacker action after May. On May 18, 2026, between 19:10 and 19:31 UTC, an attacker moved all 53 tags of actions-cool/issues-helper and all 15 tags of actions-cool/maintain-one-comment to unsigned commits authored as Jinke Li with the message "Build action for <tag>", each running a Mini Shai-Hulud payload before delegating to the genuine action so the workflow still succeeds. GitHub disabled both repositories on May 19, which stopped downloads but left every malicious tag in place. On September 16, between 09:09 and 16:16 UTC, the repositories became downloadable again with those tags untouched, so any workflow calling the actions by tag (@v2.1.1, @v2.2.0, @v2.2.1, @v3) executed the payload on its next run, resolving v3 to commit 147337a919d9. The payload is byte-identical to the May build, Git blob 2931c1be43b0d04174636ddbff54963aec92bdeb at 500,143 bytes, and GitHub disabled both repositories again on September 25.

issues-helper alone lists about 15,000 dependent repositories on GitHub's dependency graph, and workflows that call it run daily or on every issue event, so most exposed projects ran the payload within a day of re-enablement. SafeDep confirmed six fresh infections between September 20 and 24, including jd-opensource/micro-app with 6,254 stars and ant-design/pro-components with 4,833, and five of the six triggers are unattended issue bots, meaning the infection repeats on schedule with the attacker gone. The lesson is that disablement is not remediation: containment that depends on repository visibility is reversible by one unexplained re-enablement, and Socket could not determine who requested it or why. The second argument sits in the payload's targeting. On a runner it reads the ghs_ token from Runner.Worker memory and commits hook files that GitHub displays as Verified commits from github-actions[bot], defeating the review control most maintainers actually trust. But the kitty-monitor backdoor installer deliberately skips CI and waits for a developer to open the project through a Claude Code SessionStart hook or a VS Code folderOpen task, so the CI token is the entry point and the workstation holding SSH keys, cloud credentials, and password manager vaults is the objective.

The immediate sweep is to search every .github/workflows/ directory for uses: actions-cool/issues-helper@ and actions-cool/maintain-one-comment@, treat any tag reference as affected, and remove the actions or pin to a full commit SHA predating May 18, 2026, since SHA pinning only protects if the pinned commit is itself clean. For any workflow that ran a tag reference on or after September 16, rotate every secret the job could reach and audit what its GITHUB_TOKEN was allowed to do. In Actions history, hunt for scheduled runs that failed in seconds at Set up job with "Repository access blocked" before September 16 and then ran 5 to 11 minutes afterward, for runner logs downloading oven-sh/setup-bun and executing bun run $GITHUB_ACTION_PATH/index.js, and for default-branch commits adding .claude/settings.json, .claude/setup.mjs (blob 0bbd3d17062ded7c8159ffe22d0a4f3a85e4823e, 5,346 bytes), or .claude/index.js; searching commit history for the markers firedalazer and thebeautifulmarchoftime catches payload commits that copied a legitimate predecessor's message. On endpoints, block t.m-kosche[.]com and check developer machines for ~/.local/share/kitty/cat.py, ~/.local/bin/gh-token-monitor.sh, kitty-monitor systemd user services or com.user.kitty-monitor.plist LaunchAgents, and /etc/hosts entries pointing stepsecurity.io at 127.0.0.1. Sequence endpoint cleanup with token rotation: the wiper, rm -rf ~/ plus ~/Documents, fires when the stolen token starts returning 40x, so revoking credentials on a machine that still runs the monitor can trigger disk destruction.

Two developments would move this assessment. Any explanation of the September 16 re-enablement, or a third flip of either repository's accessibility, would settle whether this was maintainer error or deliberate actor action, and the malicious tags remain in both repositories either way. The other is scale: SafeDep's six-repository list came from GitHub code search and is explicitly a floor, so wider sweeps finding the hook files or new victims after the September 25 re-disablement would mean the exposure is still growing, and the wiper's independent trigger on a deprecation message from @cap-js/openapi@1.4.1 remains a dead-man switch outside anyone's control.
