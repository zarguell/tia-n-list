Attackers deploying the Anubis ransomware hit a U.S. organization in October 2026 using a previously undocumented custom backdoor that Symantec calls Backdoor.Lindnor. The implant was found on the only two Microsoft SQL Server machines in the environment, masquerading as a Chrome component on one host as healthcontroller64.exe and as a VMware file on the other as svchelper.exe, running as a service in both cases. The encryption payload iservice.exe, which appends the .anubis extension and drops ransom notes named restore files.txt and restore files.html, was blocked before execution and Symantec reports no evidence that any files were encrypted. The operation also dropped at least 13 executables within roughly an hour to terminate security products, five of them signed but vulnerable drivers used in a bring-your-own-vulnerable-driver approach, and installed AnyDesk with a safemode.exe helper that registers the tool to run in Safe Mode via HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Network\AnyDesk. Command and control ran over port 443 to a primary and a fallback server, and Lindnor has also been seen on the networks of two unrelated organizations without ransomware activity.

This incident stands out from the usual ransomware playbook because few operators build their own backdoors, and the volume of defense-disabling tooling used inside a single hour is unusual even by Anubis standards. Symantec attributes Anubis to Hawkmoth, a ransomware-as-a-service operator that emerged in December 2024 as a rebrand of Sphinx and that has claimed roughly 96 victims in the past twelve months, 52 percent of them in the U.S. The group's affiliates carry out the intrusions, so tradecraft varies, but the October case shows deliberate preparation for security tooling: callback removal via the -d switch leaves an EDR agent running but blind, and the Safe Mode route gives the operators a window where most security software does not fully run. The encryption phase failed, yet a custom backdoor with data-exfiltration capability sat on database servers for the duration of the intrusion, and the ransom note claims data theft, so defenders should treat this as a full incident rather than a prevented one.

There is no patch for a backdoor; response is containment and hunting. Isolate affected SQL Servers without rebooting them, preserving memory and logs, and hunt for new services in the System log under event ID 7045 and the Security log under event ID 4697, especially services whose binaries sit in Chrome- or VMware-named folders on hosts that do not run those products. Review outbound port 443 from database servers for long-lived HTTPS sessions to rare hosts, particularly paired destinations where one appears only when the other fails, and block the documented command-and-control hosts msrcontrib[.]com and cfgsync-relay.eastus.cloudapp.azure[.]com. Check driver loads for havoc.sys, monprocessex.sys, xhunter1.sys, bdapiutil64.sys and fly.sys, AnyDesk installations, new local users added to local groups, and the presence of iservice.exe, huntreagent.exe and s1.exe. File hashes published by Symantec for Backdoor.Lindnor include fc200686175559f4544a5de826905f09a68476d889690a3be40ac32356790cb8 for healthcontroller64.exe and svchelper.exe, 5d2dd9caf2ae4a5083dbec16e688040456cdbc31eaeecbab78188e322ed0415b for powerhost.exe and eventwatcher.exe, and ad9575a9ef2dcc9d2fd2a24376c418549d4b3db5564c22b20081d33cf7629e43 for volumeproxy.exe.

The assessment changes if Lindnor reappears in additional intrusions, which is plausible given it has already surfaced on two unrelated networks, or if Symantec identifies the initial access vector it could not determine in this case, which would reset exposure estimates for organizations running internet-facing SQL Server. Follow-on reporting on whether any data was actually exfiltrated, and whether Hawkmoth affiliates adopt the Safe Mode technique more broadly, would also change the priority defenders should assign to this intrusion.
