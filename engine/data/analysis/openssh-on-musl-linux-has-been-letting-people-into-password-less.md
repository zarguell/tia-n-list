OpenSSH on Linux systems built on the musl C library has been letting attackers into password-less accounts since 2016. On musl-based systems where sshd checks passwords itself instead of using PAM, including Alpine Linux, OpenWrt, Buildroot, and Yocto, accounts configured to block password logins by replacing their password hash with an asterisk in /etc/shadow will accept any password between 257 and 1024 bytes. The flaw, nicknamed sshole and tracked as CVE-2026-123158, was discovered by researcher Ozgun Kultekin and stems from a 2016 patch for CVE-2016-6210 that made OpenSSH perform password hashing even for accounts with no usable hash; musl's crypt() returns an asterisk when hashing fails, including on oversized passwords, which collides with the disabled-account marker. OpenSSH 10.6p2, released November 5, 2026, ships a workaround, and developer Damien Miller advised administrators to set PasswordAuthentication to no or disable SSH entirely.

CISA added CVE-2026-123158 to the Known Exploited Vulnerabilities catalog on November 9, 2026 based on exploitation evidence, and Alpine Linux published an advisory with fixed packages in OpenSSH 10.6p2. The story tracks CVE-2016-6210 and CVE-2026-123158 across forty sources. The flaw requires a specific configuration, musl libc with PAM disabled, so glibc-based distributions are not affected, but any internet-facing sshd on a musl-based system with disabled-password accounts is exposed.

What to watch: the federal patch deadline tied to the KEV listing, confirmation of in-the-wild exploitation campaigns, whether musl-based distributions ship fixed OpenSSH builds beyond the 10.6p2 workaround, and whether accounts with asterisk password hashes were actually reachable on exposed systems.
