OpenSSH built against musl libc and running without PAM has let anyone log in to password-locked accounts since 2016. The defect is in musl's crypt() for the SHA-256 and SHA-512 hash types ($5$ and $6$): a password longer than 256 bytes is refused, and crypt() returns the literal string "*". sshd compares that returned "*" against the /etc/shadow password field, which is exactly "*" for locked or passwordless accounts such as root and key-only deploy users, so the match succeeds and any long password authenticates. OpenSSH rates the flaw critical and shipped OpenSSH 10.6p2 on November 5, 2026 with a workaround; Alpine has backported fixed packages to every release from 3.16 onward. The issue was documented by researcher Özgün Kültekin under the name "*sshole".

A successful login to a passwordless account is an immediate remote foothold on systems administrators believed accepted only SSH keys. The exposed population includes root, key-only deploy users, LDAP users, and the default user on Alpine's AWS and Azure images, the accounts that run production workloads and hold the broadest credentials. This story deserves the desk over the other thirty candidates because the affected base-image footprint is enormous, spanning Alpine, OpenWrt, Buildroot, Yocto, and countless Docker images, yet the fix is a single version bump and one sshd setting, so exposure persists wherever teams have not rotated to key-only auth or patched.

Patch to OpenSSH 10.6p2 immediately, or apply the Alpine backport available for every release back to 3.16. Where patching cannot happen right away, set PasswordAuthentication=no in sshd_config and restart sshd, or disable SSH entirely, as OpenSSH developer Damien Miller advised. Restrict sshd to key-only authentication and limit inbound SSH to known admin networks. Hunt for abuse by searching /var/log/messages and the system auth log for "Accepted password" events against accounts whose /etc/shadow entry is exactly "*", since any such login is by definition unauthorized.

Watch for a formal CVE assignment and for GreyNoise or Shodan telemetry showing active scanning for long-password SSH logins against musl-based hosts, which would confirm exploitation in the wild. Also watch whether OpenSSH or musl issues a deeper fix in crypt() itself rather than a sshd-side workaround, since that would determine whether the underlying condition is truly closed.
