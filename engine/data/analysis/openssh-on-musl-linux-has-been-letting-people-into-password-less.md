A flaw nicknamed *sshole lets attackers log into Alpine Linux and other musl-based OpenSSH accounts that are configured to block password authentication, simply by submitting an oversized password. Disclosed by researcher Ozgun Kultekin, the issue has existed since 2016 and affects OpenSSH on musl libc systems including Alpine, OpenWrt, Buildroot, and Yocto. Normally an account whose /etc/shadow hash is an asterisk rejects every password, but a 2016 patch for CVE-2016-6210 made OpenSSH run password hashing even for accounts without a usable hash, in order to defeat timing-based username enumeration.

The musl C library's crypt() returns an asterisk when hashing fails, including for passwords longer than 256 characters, so OpenSSH compares the submitted hash against the stored asterisk and grants access. Passwordless accounts therefore accept any sufficiently long password. OpenSSH developer Damien Miller advises setting PasswordAuthentication to no, restarting sshd, or disabling SSH entirely. OpenSSH 10.6p2, released on November 5, 2026, ships a workaround.

Treat the bug as narrow but severe where it applies: it requires musl and a non-PAM password-checking configuration, yet it defeats the standard practice of locking an account with an asterisk, and the *sshole disclosure itself carries no CVE. Administrators of Alpine, OpenWrt, Buildroot, and Yocto devices should check whether sshd accepts oversized passwords on asterisk-locked accounts and apply the OpenSSH 10.6p2 workaround.
