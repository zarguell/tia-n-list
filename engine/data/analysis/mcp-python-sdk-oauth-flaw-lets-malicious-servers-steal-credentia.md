The vulnerability is in Anthropic's official MCP Python SDK: vulnerable releases 1.9.1 through 2.1.1 fail to validate the authorization server issuer during OAuth discovery for HTTP transport clients. A malicious MCP server can return a 404 during modern discovery, forcing an unsafe fallback that accepts attacker-controlled OAuth metadata specifying an attacker token endpoint. Client secrets, authorization codes, and PKCE proof keys are then redirected to the attacker, enabling account takeover against identity providers such as Okta, Google, and Microsoft Entra ID. The events carry no CVE assignment and list affected SDK versions explicitly.

This is not a generic SDK bug: the deception relies on the victim still seeing a legitimate identity provider login page while the authorization code is silently redirected to an attacker-controlled endpoint. The three news sources (cyberpress.org, gbhackers.com, thehackernews.com) and the Mastodon update all reference the same Cycode disclosure, with the update specifying version 1.30.0+ as the patched release. Because HTTP-based MCP clients connect to arbitrary servers, the exposure is broad for any deployment that uses vulnerable SDK releases and relies on OAuth providers without issuer validation; the score of 5.1 reflects limited but credible pickup.

Defenders should upgrade to SDK version 1.30.0 or later, the exact remediation mentioned in the Mastodon update. For environments that cannot patch immediately, restrict HTTP transport MCP clients to known, trusted server endpoints and audit network connections for unexpected token endpoint traffic. Hunt for evidence of compromise by reviewing OAuth authorization flows that reference unexpected token endpoints; check SDK logs for 404 responses during authorization-server discovery followed by fallback configurations, and inspect for attacker-controlled endpoints in OAuth metadata returned by MCP servers.

Watch for a vendor advisory from Anthropic assigning a CVE and for any exploitation telemetry showing malicious MCP servers actively returning forged 404 discovery responses. A second development to monitor is whether patched releases beyond 1.30.0 address additional discovery-path weaknesses not covered in the current disclosure.
