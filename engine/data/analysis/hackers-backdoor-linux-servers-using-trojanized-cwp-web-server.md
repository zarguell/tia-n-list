CWPdoor is a passive Linux backdoor distributed through a trojanized cwpsrv binary, the web server behind the Control Web Panel (CWP) management interface. Attackers replaced legitimate cwpsrv versions 1.15.10 and 1.24.0 with a recompiled binary containing malicious code planted in the panel's own source. XLab first captured the installer script cwpsrv_update.sh on June 29, 2026; it downloads the payload from 136.0.141.71 and overwrites /usr/local/cwpsrv/bin/cwpsrv. The implant stays dormant until an HTTP request arrives with the X-Ngx-Integrity-Data header holding an AES-encrypted command, validated by an X-Ngx-Integrity-Time timestamp and an X-Ngx-Integrity-Sig RSA signature checked against an embedded public key. Successful triggers run commands through a helper process over the ngx_http_integrity_helper Unix socket and return output in an application/octet-stream response, while suppressing the request from access logs.

The exposure base is large: XLab observed more than 340,000 CWP instances on the public web in the preceding month, and the researchers found real-world infection evidence, including a cwpsrv.suspeito sample uploaded to VirusTotal from Brazil on September 30, 2026, with zero detections, packed inside evidencia.tgz alongside an Ebury backdoor. Because the hosting panel runs as root, a successful compromise gives the attacker command execution plus reach into hosted websites, email and DNS on every co-located domain - a durable foothold, not a noisy intrusion. This is the story to watch over the other Linux malware reports because the backdoor is passive and log-suppressing: normal patching and log review will not reveal it, so a server can be owned long after the binary swap.

Defenders should verify the integrity of cwpsrv on versions 1.15.10 and 1.24.0, rebuild or restore from clean media, and hunt for the ngx_http_integrity_helper socket using ss -axp | grep integrity plus unexpected cwpsrv helper or worker processes. Outbound contact to 136.0.141.71, the IP used by the installer to fetch the trojanized binary, should be blocked or alerted. Since no CVE or vendor fix was disclosed, binary integrity checks and rebuilds are the primary remediation, and any panel access occurring without a matching log entry should be treated as suspicious given the log-suppression behavior.

Watch for a Control Web Panel advisory or CVE assignment, a confirmed victim count, and any clarified link between CWPdoor and Ebury, which XLab said remains unclear; any of those would change the exposure assessment.
