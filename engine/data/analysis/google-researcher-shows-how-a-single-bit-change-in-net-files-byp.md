Google Project Zero researcher James Forshaw published a write-up showing that a change in how the .NET Framework loads a program file can let a local attacker run untrusted code past protections built to stop it. The reported technique is a single-bit flip in a .NET PE header. According to the coverage, the same loading behavior bypassed two separate Windows protections and also defeated Oracle VirtualBox process hardening on Windows hosts. CVE-2026-87268 is the identifier attached to the VirtualBox case; the Windows code integrity bypass is described in the same write-up.

The social coverage names the Windows side more specifically: the header change bypasses Windows Code Integrity and User Mode Code Integrity on Windows 11 in S Mode. That matters because S Mode and UMCI are meant to allow only trusted, signed code. A local attacker who can alter one header bit and still get the file loaded turns a signing control into a loader parsing quirk. The report is framed as local exploitation, not a remote campaign, and the available text gives no victim count or evidence of in-the-wild use.

The concrete artifacts to track are the modified .NET PE header state and the affected loading path, plus CVE-2026-87268 for the VirtualBox hardening bypass. Watch for Microsoft or Oracle guidance on validating .NET PE headers and for detection advice around unexpected .NET binaries with modified headers on UMCI-enforced hosts. Until a fix is confirmed, code integrity on those hosts should not be treated as a hard barrier against locally supplied .NET files.
