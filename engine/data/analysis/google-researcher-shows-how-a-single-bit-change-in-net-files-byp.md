Google Project Zero researcher James Forshaw published the technical write-up on 23 November. The mechanism is a loader fallback in .NET Framework 4: PEImageLayout::Map tries MappedImageLayout with an SEC_IMAGE mapping, and when CreateFileMapping fails with STATUS_INVALID_IMAGE_FORMAT it uses FlatImageLayout, which maps the assembly as data and never presents an image section to code-integrity checks. VirtualBox on Windows triggers that status itself because its hardened NtCreateSection hook maps an AnyCPU managed assembly to VERR_LDR_ARCH_MISMATCH; that bypass is CVE-2026-87268, CVSS 7.8, affecting Oracle VM VirtualBox 7.2.16. For Windows code integrity, clearing the IMAGE_FILE_EXECUTABLE_IMAGE bit in the COFF header produces the same failure and yields CVE-2026-108398, CVSS 8.8. Both are local, low-privilege issues; the write-up reports a proof of concept, not in-the-wild use.

The argument is that one flipped bit defeats two controls that defenders buy as separate layers, and one of them still has no fix. The October 13 update repairs the WLDP policy check so UMCI enforcement on Windows 11 S Mode rejects the modified assembly, but Forshaw says it does not change protected-process behavior: a COM hijack against a class loaded by WerSecureFault.exe still places arbitrary .NET code in a PPL process at the TCB level without administrator rights, and Microsoft treats PPL bypasses as out of scope. The VirtualBox case is likewise host-side code execution inside a protected VM process, not a guest escape. There is no fleet-wide victim count in the reporting; the exposed set is any Windows host where a low-privileged user can drop a DLL and register a COM object, with the two CVEs, build 7.2.16, and the S Mode test as the concrete markers.

Patch Windows hosts with the October 13 cumulative update matched to the OS and framework version: KB5127694 for Windows 11 26H2 with .NET Framework 3.5 and 4.8.1, KB5127690 for 24H2 and 25H2, KB5127687 for Windows Server 2022 with .NET Framework 4.8, and KB5128927 for the Server 2012 R2 rollup. Move VirtualBox 7.2.16 hosts to the September CSPU build 7.2.18 or later. Dynamic Code Security blocks the loader path but also disables dynamic .NET loading, including Assembly.Load from a byte array, so use it only where the application impact is understood. There is no network vector to filter; hunt in process telemetry for C:\Windows\Microsoft.NET\Framework64\v4.0.30319\regasm.exe invoked with /unregister against a user-writable DLL, for per-user COM registrations that point at .NET assemblies, and for assemblies missing the IMAGE_FILE_EXECUTABLE_IMAGE characteristic on hosts that run hardened VirtualBox or WerSecureFault.exe.

Watch for Microsoft closing the PPL route or assigning it a CVE, since the October fix explicitly leaves that boundary alone. Also watch for any report of this loader path outside Forshaw's proof of concept; observed use against UMCI-enforced or S Mode endpoints would move the issue from patch-lag risk to active compromise.
