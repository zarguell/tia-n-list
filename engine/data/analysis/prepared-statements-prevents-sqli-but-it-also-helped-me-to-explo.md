CVE-2026-6460 is a type-confusion flaw in PostgreSQL core rated CVSS 8.8 (AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H) that lets any database user who can create objects execute arbitrary code as the operating-system user running the server. The bug dates to PostgreSQL's ability to change a column's type, introduced May 5, 2004, and the researcher's exploit path relies on expanded-object pointers added May 14, 2015. The trigger is a prepared statement holding a composite-type value whose field type is then altered (for example from UUID to bytea) before EXECUTE; the server reads the stale value under the new type, interprets controlled bytes as an expanded-object header and pointer, and follows a forged methods table to attacker-chosen native code. PostgreSQL 18.7, 17.12, 16.16, 15.20, and 14.25 fix it alongside 51 other flaws, 32 of them rated 8.8 and 31 of them also code-execution issues.

The privilege bar is low and the blast radius is high: any role with CREATE or object-alter rights on a composite type can reach OS-level code execution, and managed PostgreSQL estates (Aurora, RDS, Azure PostgreSQL, AlloyDB, Supabase, Databricks, Ubicloud) were privately notified with working proof-of-concept code in August 2026, so patch status across those platforms is uneven. The research also turns a defensive control against the defender, since prepared statements, the standard SQL-injection mitigation, are the vehicle that pins the stale value in place while its type is changed. This story matters more than the other thirty today because the fix is not a package upgrade alone; full protection requires rebuilding every C-language extension installed on the server, a step automated patching will skip and that leaves the primitive reachable even on a patched core.

Upgrade to PostgreSQL 18.7, 17.12, 16.16, 15.20, or 14.25 (the last 14.x release, since PostgreSQL 14 reaches end of life with this update), then rebuild all installed C-language extensions before returning the instance to service. Restrict object-creation and ALTER rights on composite types to trusted roles, review database accounts for unnecessary CREATE privileges, and inspect backend logs for unexpected signal-11 crashes during EXECUTE of prepared statements or type changes on composite types. On managed platforms, confirm the provider's patched build and extension rebuild status rather than assuming the control plane handled both.

Watch for publication of the full exploit chain (the researcher withheld the final code-execution SQL), for provider-specific advisories confirming rebuilt extensions, and for any in-the-wild use; the PostgreSQL Global Development Group reports no known exploitation at release, but the public research and the August proof-of-concept sharing lower the barrier. Also track whether any extension rebuilds are missed in automated pipelines, since that is the residual exposure after patching.
