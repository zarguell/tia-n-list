CVE-2026-6460 is a PostgreSQL type confusion with a CVSS score of 8.8 that Mehmet Ince traced to behavior dating to 2004. His writeup describes preparing a query, changing a field's type with ALTER SET DATA TYPE and then executing the prepared statement. The prepared value is not rewritten for the new type, so bytea output logic reads stale bytes as an expanded-object header and pointer. A lowest-privileged login role can crash the backend this way, and the research developed the primitive toward code execution with the server operating-system account. The expanded-object pointer mechanism itself arrived on May 14, 2015, and reproducible proofs of concept were privately shared with managed PostgreSQL providers around mid-August 2026.

PostgreSQL's November 12 security release fixes CVE-2026-6460 among 52 vulnerabilities; 32 of them are rated 8.8. The versions named across the reporting are 18.7, 17.12, 16.16, 15.20, 14.25 and 19 RC 2, with PostgreSQL 14 reaching end of life in this cycle. French coverage from IT-Connect restated the 52 fixes and the 2004 origin of the type confusion. The advisory says full protection also requires rebuilding C-language extensions installed on the server, because the fix changes how those extensions interact with the server.

The practical risk is that a role able to create objects can turn a legal SQL feature into server-side code execution, and patching the server binary alone can leave extensions mismatched. Watch for packager guidance on which extensions need rebuilding, confirmation of exploitation outside the private proof-of-concept set, and whether managed providers report incidents from the August notifications. Administrators should inventory server builds and compiled extensions together.
