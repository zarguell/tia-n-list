Meta's Muse, launched September 8, runs each user's agent in a dedicated 2-vCPU, 8 GiB Cloud Hypervisor VM with a systemd-nspawn runtime container, a host-side Sentinel egress gate and a separate credential service. NebuSec showed that asking the agent to export an attacker-controlled page through bundled Chromium, observed at 152.0.7977.82 in early October and later at 155.0.8059.80, gave code execution through V8 issue 554034656 while the PDF-export process ran without an IPC sandbox. Sentinel's read and write policy let GET-only traffic carrying conversation history and stored memories leave without an approval prompt; generated exploits against Linux 7.0.0-39-generic then escaped the container to VM root and exposed secure credential storage. This was a laboratory demonstration, not real-world exploitation, it stayed inside one user's VM, and Meta had not publicly confirmed the fixes at publication.

That chain matters because the exfiltration path survived the control built to stop it, and the weakness is architectural rather than a single parser bug. Sentinel sits outside the runtime container but inside the user VM, so after kernel root the same policy point can be bypassed entirely; reads beneath the 2 MiB per-originator and 5 MiB per-domain 60-minute budgets can leave silently, making theft look like ordinary browsing rather than an alertable breach. The exposed surface is one user's 2-vCPU, 8 GiB machine and its 100 GiB LUKS2/Btrfs store, including conversation history, memories, connector tokens for services such as Gmail, Notion and Facebook, and Sentinel itself. Scope is bounded by Cloud Hypervisor isolation, but this is a reference design for how sandboxing, privilege separation and network monitoring can each work as intended and still leave a credential store reachable by a page the agent was asked to render.

Treat browser-to-PDF export as code execution and disable or tightly gate untrusted page export until Meta names fixed builds; no fixed Chromium or kernel version is given in the reporting, so the 155.0.8059.80 snapshot is not a patch line to copy. Hunt in Sentinel policy and process-attribution records for GET requests carrying conversation or memory content, for execd taint states other than clean, and for originators approaching the 2 MiB or 5 MiB rolling egress thresholds, then review chat history and stored memories for edits as an integrity problem. At the VM layer, watch for traffic that does not traverse the Sentinel proxy at 198.19.0.1:3128, kernels matching 7.0.0-39-generic, and unexpected access to the 100 GiB LUKS2/Btrfs volume, /boot, /run/hatch/privsep or /opt/hatch/runtime-cell/guest.env. Rotate or reapprove connector credentials for accounts that exercised the feature, and use Meta's published bug bounty, which offers up to $300,000 including $130,000 for prompt injection affecting one user, when reporting related findings.

Watch for a Meta advisory naming CVEs, affected Chromium and kernel builds, and a fix that moves egress enforcement to the VM boundary rather than only the container cgroup. The second trigger is any evidence of real-world use or a Cloud Hypervisor guest-to-host escape, either of which would move this from a contained lab chain to a cross-tenant incident.
