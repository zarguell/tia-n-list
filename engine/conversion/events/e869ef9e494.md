Miggo Security discovered two access-control vulnerabilities in RabbitMQ, both present since version 3.13.0 (early 2024). **CVE-2026-57219** (CVSS 8.7) is the more severe: an obsolete management endpoint (`GET /api/auth`) returns the broker's confidential OAuth client secret to any unauthenticated requester. In deployments using OAuth with Entra ID, Auth0, Keycloak, or UAA, an attacker can exchange the leaked secret for an administrator token and gain full broker control — reading, modifying, and deleting all messages, creating users, and altering configuration.

**CVE-2026-57221** (CVSS 5.3) is an authorization bypass in passive queue/exchange declaration operations. Even zero-permission accounts can enumerate queues and exchanges and retrieve metadata (message counts, consumer counts) in shared environments, enabling tenant reconnaissance.

Both are fixed in versions **4.3.0, 4.2.6, 4.1.11, 4.0.20, and 3.13.15**. **Patching alone is insufficient for CVE-2026-57219** — organizations must rotate the OAuth client secret after upgrading, as the leaked credential remains valid until rotated.

**Hunting hypothesis:** An unauthenticated attacker discovers a RabbitMQ management interface on port 15672, sends a single GET request to `/api/auth` to retrieve the OAuth client secret, exchanges it with the identity provider for an admin token, and takes full control of the message broker — intercepting orders, payments, and authentication events flowing through enterprise microservices.
